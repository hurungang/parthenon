## Description

## Problem Statement

The current MVP agent for kiosk monitoring has proven valuable, but it is a one-off solution. To support future AI agent use cases and ensure secure, scalable operations, we need a robust platform framework. This framework must enable rapid onboarding of new agent modules, enforce strong security and identity controls, and provide operators with the tools to manage use cases and environments efficiently.

## Goal

Deliver a sustainable, extensible agentic platform framework that can host the MVP and future AI agent modules, with centralized management of security, identity, environment profiles, and user access.

## Key Capabilities

  * Management portal for operators to manage use cases and run AI agents
  * Module-based architecture: each AI use case is a module with its own UI and setup requirements
  * Environment profile management: configure and select environment profiles per use case (e.g., test/prod, with separate secrets and identities)
  * Agent identity management: manage agent user identities and Keycloak integration for sign-in and token refresh
  * Trigger user identity passthrough: always pass the identity of the user who triggered the agent to the use case
  * User access control: manage permissions per use case and environment profile



## High-level Acceptance Criteria

  1. Operators can view, add, and manage AI agent modules via the management portal
  2. Each module can declare its required secrets, agent identity, and settings
  3. Operators can create and manage environment profiles for each use case, storing required secrets and agent identity
  4. When running a use case, operators can select which environment profile to use
  5. The system manages agent user identities, including sign-in and token refresh via Keycloak
  6. The identity of the user who triggers an agent is always passed to the agent module
  7. User access control is enforced per use case and environment profile; users can only access what they are permitted
  8. All sensitive credentials and PII are protected according to security requirements



## Out of Scope

- Implementation of individual agent modules beyond the MVP and initial framework  
- Detailed UI/UX design or technical architecture decisions  
- Integration with non-Keycloak identity providers

## Dependencies & Constraints

- Requires integration with Keycloak for agent identity management  
- Must comply with existing security and PII protection standards  
- Dependent on continued support for the MVP kiosk monitoring agent as a module

## Description

## Context

Current reporting services lack auto-scaling capability, leading to infrastructure failures (disk full, out of memory) during traffic spikes. [INTSSSSB-1776](https://jira.amadeus.com/agile/browse/INTSSSSB-1776 "No Data Flow for NORAM Region from 29th Oct 2025 for ABD CUSS Feeds") (JFK disk full causing 24+ hour data loss) demonstrates the impact of this limitation.

## Solution

Migrate reporting services to Kubernetes (EKS) with auto-scaling implementation to dynamically allocate resources during traffic spikes and prevent infrastructure failures.

## Business Value

  * **Prevents Infrastructure Failures:** Eliminates disk-full and out-of-memory incidents
  * **Dynamic Resource Allocation:** Auto-scaling responds within 2 minutes to traffic spikes
  * **Cost Optimization:** infrastructure cost reduction
  * **Improved Resilience:** reduction in resource-related outages



## Requirements

  * Migrate all reporting services to Kubernetes (EKS)
  * Implement horizontal pod autoscaling (HPA) for all reporting components
  * Define auto-scaling policies (CPU, memory, custom metrics)
  * Implement resource quotas and limits
  * Configure pod disruption budgets for high availability
  * Validate auto-scaling behavior under load
  * Document Kubernetes deployment and scaling configurations



## Expected Value (Benefit Hypothesis)

Kubernetes infrastructure configured and validated in test environment. Auto-scaling response time <2 minutes validated under load testing. Configuration ready for pilot deployment.

## Definition of Done

  * Kubernetes (EKS) cluster configured for reporting services
  * All reporting services containerized and Kubernetes manifests created
  * Horizontal pod autoscaling (HPA) configured and tested
  * Auto-scaling policies defined (CPU, memory, custom metrics)
  * Resource quotas and limits configured
  * Pod disruption budgets configured
  * Auto-scaling validated under load testing with <2 minute response time
  * Resource optimization validated in test environment
  * Monitoring and alerting integrated with Kubernetes metrics
  * Documentation completed and accepted
  * Operations team trained on Kubernetes management
  * Configuration ready for pilot deployment



## Dependencies

  * Kubernetes cluster availability (EKS)
  * Infrastructure team coordination for cluster configuration
  * Load testing environment for validation
