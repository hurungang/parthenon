# Implementation Plan: CC Assistant Management Tool Coverage

## Overview

Close the capability gap between the Control Center Assistant's `cc____` management tools and the web UI management forms across all nine registered resource families (skill, sop, agent_type, agent_role, agent_identity, model_config, schedule, data_type, mcp_server). The work proceeds bottom-up: first audit the exact per-family field parity, then extend the CC internal handlers with full UI field sets + typed validation + structured actionable errors, then publish typed per-resource tool parameter schemas in the registry (preserving stable UUID allocation and parity pairs), then extend the confirm-before-write preview tables, and finally prove everything with backend tests per family plus an assistant-conversation E2E.

Constraints honored throughout: confirm-before-write flow unchanged; permission parity per `(resource_type, action)` untouched; `cc` MCP entity remains seeder-managed (never reuse/change deployed `mcp_hub_id`s); no delete verb; only CC writes the database; no frontend changes.

- [x] 1.2 — Audit tool-accepted fields per family — _Done when: for each family, the fields currently accepted by `backend/app/api/v1/internal/management_tools.py` create/update handlers (`_build_create`, `_apply_update`) and read serializers (`_SERIALIZERS`) are enumerated; known gaps confirmed (update_agent_type missing role_id / identity_id / input_type / output_type / output_data_type_id / input_schema / output_schema / guardrails; update_agent_identity missing role assignment + status; update schedules missing cron/payload; update data_types missing description/slug semantics; serializers missing fields the UI detail views show — e.g. agent type guardrails + output_data_type_name, identity role assignments, role sop/skill grant lists, mcp server auth/credential posture flags)._

### Phase 2 — CC Internal Handlers: Full Field Sets + Typed Validation + Structured Errors
- [x] 2.1 — Build shared payload validator/normalizer component — _Done when: a new CC-side module (e.g. `backend/app/services/agents/management_payload.py`) provides typed field coercion (enum coercion with the valid values listed in the error), UUID/id-or-name FK resolution (tenant-scoped, 404 with actionable message on unknown), required-field enforcement, unknown-field rejection, and a structured validation-error builder (field, problem, remedy hint); unit-tested in isolation._
- [x] 2.2 — Extend agent_type create/update to full UI set — _Done when: create_agent_type and update_agent_type accept and apply every field from `AgentTypeCreate`/`AgentTypeUpdate` in `backend/app/schemas/agents.py` (name, description, identity_id, role_id, model_id, is_active, system_instruction, input_type, input_schema, output_type, output_schema, output_data_type_id, all eight guardrail fields, skill_bindings, sop_bindings) via the validator; the conversational-input-type vs output_data_type_id conflict returns a structured error mirroring the REST validator; guardrail contract validation matches `_validate_guardrail_contract`._
- [x] 2.3 — Extend agent_identity create/update incl. role assignment — _Done when: update_agent_identity accepts name, realm_name, realm_username, status (enum-coerced) and role_ids (id-or-name, additive-merge semantics consistent with the existing binding helpers, resolve-before-write, unknown → 404, no partial write); create_agent_identity accepts the full `AgentIdentityCreate` set including status; identity create/update never touches tokens or credentials._
- [x] 2.4 — Extend remaining families to full UI sets — _Done when: update handlers accept every UI-editable field per matrix: skill (name, description, instructions, is_active), sop (same), agent_role (name, description, skill_ids, sop_ids), model_config (display_name, provider_type, api_base_url, enabled_models, is_disabled — api_key write-accepted but never echoed), schedule (name, description, cron_expression, payload, target_type, target_id, is_active/status where UI supports), data_type (name, description, fields, and slug only where the REST update schema permits), mcp_server (name, description, base_url); each writes only through CC handlers (top-priority rule)._
- [x] 2.5 — Replace bare 400 strings with structured error payloads — _Done when: every validation failure in the management-tools handlers returns a structured payload (error code, per-field problems, remedy hint naming the correct tool or valid enum values); existing generic errors like "slug is required" become field-specific actionable messages; permission denials (403), not-found (404), and duplicates (409) keep their semantics but carry the structured shape; existing behavior for non-validation errors unchanged._
- [x] 2.6 — Keep read serializers at UI-detail parity — _Done when: serializers return the fields the UI detail views show (agent type incl. guardrails + output_data_type_name + input/output types; identity incl. role assignments; role incl. skill/sop grant ids; data type incl. fields; mcp server incl. non-sensitive posture fields); no credential/token/secret ever appears in any serializer output; verified by unit test._
- [x] 2.7 — SOP steps parity (nested structure correction) — _Done when: create_sop / update_sop accept a typed `steps` array via the payload validator (order int; step_type enum skill_invocation|agent_delegation; skill_id REQUIRED and tenant-scoped id-or-name resolved on skill_invocation steps; target_agent_type_id REQUIRED and resolved on agent_delegation steps; unknown per-step fields and the skill_id-XOR-target violation return structured errors); semantics mirror REST `PUT /sops/{id}/steps` (full-list replace, delete + recreate in order) and invalidate the shared permission-manager cache for every role bound to the SOP; `_serialize_sop` returns the ordered steps so get_sop / list_sops reflect them; integration-tested in `backend/tests/integration/test_management_tool_full_field_parity.py`._
- [x] 2.8 — Agent-role MCP session mappings — _Done when: create_agent_role / update_agent_role accept `mcp_session_mappings` (typed `[{server, session}]` id-or-name list; session validated to belong to the server; one mapping per server; additive merge; re-mapping a mapped server to a different session → structured 409 conflict); after explicit mappings the default rules run over the role's effective MCP server set (role skills → SkillToolBinding → tools' servers): unmapped server with a passthrough session auto-maps to it, unmapped with exactly one active session auto-maps to it, unmapped with multiple non-passthrough sessions returns a structured warning listing the server and its sessions (no guessing); zero-session servers warn too; `_serialize_agent_role` returns `mcp_session_mappings` (server/session names + auth_type, never credentials); integration-tested in `backend/tests/integration/test_management_tool_full_field_parity.py`._

- [x] 3.2 — Preserve UUID allocation & parity invariants — _Done when: no `mcp_hub_id` changes and no UUID is reused (typed schema changes mutate registered tools in place, exactly as the existing enrichment does); every parity `(resource_type, action)` pair in `get_parity_map()` is unchanged; no delete verb added; a registry invariant test asserts these properties._
- [x] 3.3 — Improve tool descriptions and schema metadata — _Done when: each create/update tool description states the full field set, additive-merge semantics for list fields, and required-vs-optional distinction; enum-typed fields carry enum lists; description text matches the enriched handlers' actual accepted fields; `get_management_tool_schema` meta tool returns the enriched schemas._
- [x] 3.4 — Verify CH routing & meta-tool flow untouched — _Done when: `backend/app/communication_hub/api/internal/tool_routing.py` and the `invoke_management_tool` / `get_management_tool_schema` / `list_management_tools` dispatch paths require no change; an existing routing test suite passes unchanged; schema size per assistant context stays bounded (progressive disclosure unaffected)._
- [x] 3.5 — SOP steps typed schema — _Done when: the `sop` entry in `_MANAGEMENT_DATA_FIELDS` declares a typed `steps` array (items: order integer required; step_type enum skill_invocation|agent_delegation; skill_id / target_agent_type_id id-or-name strings required per step_type; optional name / description / step_config) and update_sop's description states the full-list replace semantics, the per-type required reference, and that delegation steps gate role permissions; create_sop / update_sop UUIDs and parity pairs unchanged; create/update_sop schemas stay under the ~8 KB bound (`test_management_tool_schemas_stay_bounded`)._
- [x] 3.6 — Agent-role mappings typed schema — _Done when: the `agent_role` entry in `_MANAGEMENT_DATA_FIELDS` declares a typed `mcp_session_mappings` array (items: `{server, session}` id-or-name objects, both required, additionalProperties false) and the create/update tool descriptions state the additive-merge semantics, the one-session-per-server rule, the default rules (passthrough preferred; single session auto-used; multiple sessions → assistant must ask the user), and the 409 re-map conflict; all `mcp_hub_id`s and parity pairs unchanged; schemas stay under the ~8 KB bound._

### Phase 4 — Confirm-Before-Write Preview Coverage

- [x] 4.2 — Guide self-correction with structured errors — _Done when: the assistant knowledge instructs the assistant to consume the structured validation-error payload (field + remedy) and retry autonomously; knowledge examples cover the known failure shapes (missing slug, invalid enum, unknown id/name, conversational-vs-typed-output conflict)._
- [x] 4.3 — Verify no-write on rejection/timeout paths — _Done when: existing confirmation-timeout and rejection handling in `backend/app/services/agents/runtime_executor.py` is confirmed by test to leave zero writes for any new field operation (the write happens only after approval, inside the CC handler)._
- [x] 4.4 — SOP steps preview knowledge — _Done when: the assistant knowledge corpus (`sop-composition` extension + `sop-steps-replace-semantics` entry) and the canonical preview-format entry / seeded system instruction teach: SOPs are ordered steps; skill_invocation steps reference a skill by id or name; agent_delegation steps reference a target agent type by id or name; `steps` REPLACES the whole list on update so the complete desired list is always sent; the canonical preview table shows the ordered steps (`1. skill_invocation: check-credit-score`, `2. agent_delegation: FraudCheckAgent`) as old → new on updates with the replace-semantics warning (omitted steps are deleted); covered by `backend/tests/unit/test_assistant_knowledge.py`._
