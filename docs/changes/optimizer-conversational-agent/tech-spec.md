# Tech Spec: optimizer-conversational-agent

## Technical Overview

Optimization is today a one-shot command (`POST /agents/sessions/optimize` → `__command: optimize-and-verify`) whose only escape from an unprovable script is a terminal `needs_feedback` plan. This change makes the optimizer an **optimization-mode conversation on the subject agent type itself** — the *avatar* model. An optimization conversation is an ordinary `ConversationSession` whose `agent_type_id` is the agent type being optimized and whose existing free-form `channel` carries the value `"optimization"`. There is **no seeded optimizer `AgentType`**, no second identity, no optimizer role, no permission bridge and no skill-binding rows: the conversation runs with exactly the agent type's own identity, role, model bindings and tool grants, so it can never reach further than a normal run of that agent.

Because the session's agent type *is* the subject, scope is inherent rather than assigned — there is no `scope_agent_type_id` column, no host-versus-subject distinction, and nothing a prompt-injected or drifting turn could repoint. Inside the conversation, the **optimization mission replaces the agent's business system instruction and skills**, the optimization system tools are injected, and the agent's own granted tools are used **only** by an approved, single-use live test (never by the LLM turn). The executor routes an optimization-mode conversation to the **conversational loop regardless of the agent's `input_type`** (typed or conversational), while normal business runs keep today's routing untouched.

The conversational runtime, the durable interrupt/resume machinery and the in-chat asking experience are **reused, not rebuilt**. A paused turn surfaces an approve / deny / free-text card in the chat; a live-test request is a *typed* pause naming **one saved script version** — the script is the unit of approval, and the tool-call preview on the card is derived server-side from that version's own `tools.call(...)` lines. MCP tools are assumed to work: the operator is consenting to **one end-to-end run of the script** in the real sandbox, as the agent, not to a list of tool calls. Persisted in one new domain entity that records proposal, decision and execution evidence. Approval consumes the request **once** (`pending → approved → executed|failed`, mirrored by the resume record's exactly-once marker), then that script runs once under the agent type's own identity and tenant; denial, silence and expiry keep the session replay-only. `execute_script` remains replay-only — it is never a live path.

All top-priority rules hold. Control Center alone writes PostgreSQL (conversations, settings, ledger, plans, audit). Communication Hub keeps holding identity material and injecting it per tool call; Agent Runtime is the only place a turn, a replay or an approved live operation executes. Only model **identifiers** cross service boundaries — no tokens, credentials or decrypted secrets are ever persisted in the ledger, the conversation record or the checkpoint. The optimizer never uses the agent's runtime model: the conversation resolves the tenant setting `optimizer_model_id`, which falls back at read time to the existing plan-authoring model and fails closed when neither is usable.

## Detailed Contracts

### 1. Optimization-mode conversation (channel, not a new agent)

- An optimization conversation is an ordinary `ConversationSession` created with:
  - `agent_type_id` = the subject agent type (the one being optimized),
  - `channel = "optimization"` (`OPTIMIZATION_CHANNEL` constant; `String(50)` already exists — a value, not an enum, column or constraint),
  - `triggered_by_user_id` = the authenticated operator,
  - `status = active`.
- **No agent type, identity, role, skill or binding row is created anywhere.** `AssistantSeeder` remains the only system-agent seeder; no per-tenant start-up write is added for optimization, and `AgentType.is_system` gains no optimizer row. `session_service.get_optimization_gate` keeps no `optimizer_agent_type` branch.
- Creation is a dedicated endpoint (`POST /conversations/optimization`) with `{ agent_type_id }`, not the generic `POST /conversations`, so the mode value is never client-supplied:
  - `404` unknown agent type in the tenant;
  - `403` without `agent::read` on the subject (the permission the tab already requires);
  - `422 optimization_unavailable` for the request-shape failures that are not a preconditions issue;
  - typed **and** conversational agent types are both accepted (the `input_type == conversation` guard is skipped for this channel only).
- Creation **succeeds** with `availability` populated when a precondition is missing (no successful reference execution / no usable optimizer model), because the PRD requires the conversation itself to explain what is missing. Availability is computed, never stored.
- Starting optimization *work* additionally requires the existing `agent::execute` permission on the subject — the same grant the one-shot Optimize action uses. Lacking it yields a readable refusal and starts nothing.
- There is no `scope_agent_type_id`, no "host" agent and no writable subject: `agent_type_id` is set at insert and no endpoint accepts it on update, so the subject is immutable by construction.
- Sessions are resumable and multiple may coexist per agent type; listing filters on `channel` so optimization history never mixes with business conversations, and a business conversation can never turn into an optimization one.

### 2. Turn routing — channel decides the loop, not `input_type`

- **Routing condition:** `ConversationSession.channel == "optimization"` → the conversational loop, always. `input_type` is not consulted for that decision.
- Concretely: the chat entrypoint (`ws/chat.py` → AR `POST /internal/conversation/turn` → `RuntimeExecutor.execute_conversation_turn_from_context`) is taken for every optimization session, including for agent types whose normal business runs would go through the typed execute/agent-job path. A typed agent type gains no new business entrypoint — only the optimization channel accepts turns from a chat surface.
- Normal business runs are untouched: conversational agent types keep the conversation-turn path; typed agent types keep the execute/agent-job path; integration clients, A2A and the assistant keep their current routing.
- The mode is re-resolved from `conv_session_id` on **every** turn and on **resume** (the durable checkpoint carries `agent_type_id`, and the resume service re-fetches context with the conversation id), so a paused turn cannot resume in business mode.
- In optimization mode the turn is shaped as a conversational turn: no typed-input validation, no `output_schema_prompt`, no `output_json_schema` → `response_format`, and no `input_type`-driven business prompt. Replies are free text for the operator.

### 3. Optimization mode prompt, tools and identity parity

- `get_agent_context(agent_type_id, session_id=None, conv_session_id=None)` resolves the session once. For `channel == "optimization"` it returns an optimization-mode context:
  - `system_instruction` = `compose_optimization_mission(...)`: the existing optimize-and-verify mission text (`get_command_prompt(db, OPTIMIZE_AND_VERIFY_SLUG)` + `build_command_mission(..., agent_type_id=<subject>)`, preserving operator edits to the stored prompt) extended with the conversational rules — one agent type only, replay-only default, ask instead of assuming, exact live-test request rules (list every tool + arguments, single use, refuse fan-out/session-long/out-of-capability requests), no deletion, no credentials, plan statuses (`ready` / `needs_feedback` / `failed`), observable work. This **replaces** the business `system_instruction`, SOP content and skill summaries for these turns.
  - `allowed_tools` = `get_inherent_tool_names_for(optimization_enabled=True)` (self-context + authoring tools) **plus** `system____request_live_test`. The agent type's business MCP/decision tools are **not** in the turn tool set: they are reachable only by the approved live-test runner, under the same identity, which is not LLM-driven. This is strictly narrower than a business run.
  - `model_id` / `model_config_id` = `require_optimizer_model(db)` (contract 8), never `AgentType.model_id`; failure → `412 {detail:{error:"optimizer_model_unavailable", reason_code, reason}}` (fail closed, identifiers only).
  - `identity_name`, `role_id`, `role_name`, `guardrail_policy`, `bound_sop_ids` etc. are read exactly as for a business run — unchanged, never elevated, never a proxy identity.
  - `output_schema_prompt` / `output_json_schema` are `None` and `output_type` is reported as conversational, so AR builds neither a typed business prompt nor a `response_format`; an `optimization` block carries `{mode: "optimization", subject_agent_type_id, subject_name, replay_only: true}` for AR prompt/pause handling.
- A run that is not an optimization session and not a `__command` optimize run gets today's context byte-for-byte (`conv_session_id=None` for every existing caller).
- The `__command` one-shot behaviour is preserved as the *typed* equivalent: `optimization_requested` becomes `command == OPTIMIZE_AND_VERIFY_SLUG` **or** `channel == "optimization"` for the purposes of the inherent-tool gate, and the mission text is the same source of truth.
- Skill/binding parity: the `workflow-optimization` inherent skill is still injected dynamically for these turns (no `AgentTypeSkillBinding` rows), exactly as the `__command` run does today.

### 4. Inherent scope (no scope column, server-side guard)

- The subject is `ConversationSession.agent_type_id`; scope exists because the session can only be about one agent type. Cross-agent isolation is structural: there is no field to repoint and no update path for it.
- `require_subject_match(db, conversation_session_id, requested_agent_type_id)` is applied to **every** optimization-domain handler that accepts an `agent_type_id` (`get_implementation_plan`, `get_optimized_implementation_plan`, `get_scripts`, `get_script`, `list_scripts`, `generate_script`, `execute_script`, `generate_optimized_plan`, `get_execution_log`, `request_live_test`).
  - No `conversation_session_id` on the request (one-shot `__command` runs, legacy internal callers) → today's behaviour, unchanged.
  - Session whose channel is not `"optimization"` → today's behaviour (no new guard for business conversations or the assistant).
  - Optimization session + matching `agent_type_id` → allow.
  - Optimization session + any other agent type, an absent/uncertain id, a non-optimization resource, or a delete/retire intent → structured tool result `{"status": "out_of_scope", "reason": …}` and **nothing is changed** (retire/delete are not exposed as tools at all).
- The mission prompt restates the scope (defence in depth); the server check is what makes the guarantee real. The live-test validation reuses the same subject resolution, so an approved live test cannot address another agent type's tools.
- The subject id is bound by the agent context (the optimizer is told which `agent_type_id` to pass) but the guarantee does not rely on that: a model-supplied mismatched id is refused server-side, so a drifting or prompt-injected turn cannot widen its reach.

### 5. Ask and decide (in-chat, lightweight)

- Reuses `system____human_intervene` (`intervention_type` `choice` | `text` | `approval`) → `InterveneRequest` + LangGraph `interrupt()` → `ConversationTurnResume` (`waiting_for_human`) → operator answer (`WS respond` or `POST /conversations/{id}/interventions/{request_id}/respond`) → `advance_answered_intervention` → exactly one resume dispatch → `ConversationTurn` (`intervene_response`) persisted.
- UI: the pending request renders **inline in the chat** (options + free-text through the chat input), the composer is disabled until answered, and `GET /conversations/{id}/interventions/pending` re-surfaces it on reconnect/resume. No queue, no cross-session list, no dashboard.
- Nothing new is persisted for a plain question; the answer lands in the conversation record and steers the next refinement.
- An unanswered question never triggers an assumption, a background retry, or work: the session stays `waiting_for_human` until answered or explicitly ended.
- The same chain carries the live-test approval decision (contract 6) — one decision mechanism, two payload shapes.

### 6. Live-test approval ledger and the single-use gate

**A live test runs the SCRIPT end-to-end — never an individual MCP tool call.** MCP tools are assumed to work; the approval exists to prove the script the optimizer wrote. The optimizer must save the script first (`generate_script` → `version_id`), then request a live test of that version.

- `OptimizationLiveTestRequest` (`optimization_live_tests` table) fields: `id`, `tenant_id`, `conversation_session_id`, `target_agent_type_id`, `request_turn_id`, `intervene_request_id`, `resume_id`, **`script_version_id`** (nullable FK → `script_versions.id`, `SET NULL`), `status`, `requested_operations` (JSON = **tool-call preview**), `executed_operations` (JSON, nullable = **script run record**), `expires_at`, `execution_started_at`, `execution_finished_at`, `created_at`, `updated_at`.
- `target_agent_type_id` is **derived server-side** from the session (`session.agent_type_id`), never taken from the request body, and is stored on the row so a later session edit could not rewrite the audit fact.
- `status` state machine (`OptimizationLiveTestStatus`): `pending → approved → executed | failed`, or `pending → denied | expired | cancelled`. Only `executed` / `failed` carry execution timings; denial/expiry leave `executed_operations` empty.
- `requested_operations` is the **preview, not the unit**: the ordered, de-duplicated literal tool names from `tools.call('<name>', ...)` in the approved version's `python_source` (`extract_tools_call_names`), stored as `[{tool_name, …}]` and capped at `MAX_LIVE_TEST_PREVIEW_TOOLS` (`+N more` marker) for the card. The caller never supplies it, so there is no operation list to validate, debit or execute. Immutable after creation — a changed script is a new version and a **new** request.
- `executed_operations` is the **script run record**, one entry:
  `{kind: "script_run", script_version_id, script_name, script_version_label, status, result_summary (bounded), error, duration_ms, tool_calls: [{tool_name, status, duration_ms, result_summary, error}], telemetry}` — the script-level result plus telemetry and duration, with per-`tools.call` outcomes. Written once from the run result (a failed run always leaves one record saying what failed).
- Validation at creation (nothing is written on refusal): the conversation is an optimization conversation with a subject; `script_version_id` is present, exists **in the conversation's tenant**, has `python_source`, and its `ScriptDefinition.agent_type_id` **is the subject** (`out_of_scope` otherwise); the script has at least one literal `tools.call` (`no_tool_calls`); those names are within the subject's own grants when a grant set is resolvable (`operation_not_permitted`, the same check `generate_script` applies at authoring time); one pending request per conversation (`live_test_already_pending`); a bounded per-session approved-live cap (`live_test_quota_exhausted`). Refusal codes: `out_of_scope`, `invalid_script_version`, `script_version_not_found`, `no_tool_calls`, `operation_not_permitted`, `live_test_already_pending`, `live_test_quota_exhausted`.
- Single-use gate, two layers:
  1. **Domain transition** — the execution attempt performs a conditional transition `pending|approved → execution_started` in one statement (row-level, tenant-scoped); a second attempt finds no row to transition and returns the stored outcome instead of running.
  2. **Resume marker** — the approval is consumed through `advance_answered_intervention`, so the linked `ConversationTurnResume` owns `idempotency_key` + `write_applied`; a re-delivered or replayed approval is terminal and never re-executes (the same exactly-once contract the assistant's confirmed writes already rely on).
- Expiry: `expires_at = created_at + OPTIMIZER_LIVE_TEST_DECISION_TTL_MINUTES` (proposed 15). A sweep (startup + periodic, same cadence family as `activity_reaper`) closes overdue `pending` rows as `expired`, cancels the linked intervention, resolves the resume as `unresumable/expired`, and appends the bounded-stop turn. A lazy `expires_at` check on decision prevents racing the sweep.
- Attribution is read, not duplicated: who decided and the approve/deny value come from `InterveneResponse` (`operator_user_id`, `responded_at`); the operator is also the session's `triggered_by_user_id`. Live work is attributed to that user *and* the subject agent type — there is no separate optimizer identity to attribute.
- Audit: replay evidence stays `VerificationRun` / `ScriptExecutionRecord`; live evidence is the ledger row plus `RuntimeToolCall` rows carrying `optimization_live_test_request_id`. A live row therefore makes "a real integration was contacted" unambiguous.

### 7. Replay-vs-live routing

- **Default is replay.** `execute_script` resolves the reference execution and replays recorded `tool_calls` with `ReplayToolClient`; a miss or missing transcript returns a terminal `needs_user_input` stop. No code path in verification reaches a live client. `tool_call` events are logged with the **canonical** tool name (`mcp-demo____searchFlights`, via the runtime `tool_name_map`, with `tool_raw` retained), and `ReplayToolClient` also matches canonical/sanitized-equivalent names (`mcp-demo____searchFlights` ≡ `mcp_demo__searchFlights`) so older LLM-path transcripts stay replayable.
- **The only live route** is: optimizer asks `request_live_test(script_version_id=…)` → ledger row `pending` + approve/deny intervention → turn pauses → operator decision → approved → CC consumes the approval once → CC loads the version's `python_source` (+ the reference input replay would use) → CC → CH `/internal/live-test/run` → AR `/internal/live-test/run` → **one sandbox execution of that script** under the **subject agent type's own identity, tenant and existing grants**, whose only egress is its own `tools.call(...)` → run record returned to CC → `executed_operations` persisted → resume dispatched with the record in the tool result → the model refines **without** any further live call. There is no per-operation execution and no tool-by-tool test.
- Denied / expired / cancelled / unanswered → nothing runs, no retry of the same request, plan goes (or stays) `needs_feedback` with a specific "what is missing" reason, session replay-only.
- A sandbox violation, resource-cap termination or permission denial during the run stops it: the script does not continue, the ledger becomes `failed`, the failure is shown in the chat, and the session returns to replay-only. (A script that names an out-of-grant tool statically starts no work at all — the AR runner checks the preview before executing; dynamic names are refused per call by the CH permission layer, which stops the run.)
- No "always allow", no remembered approval, no automatic second test: later needs are a new request with a new approval.

### 8. Optimizer model resolution and fallback

- Tenant setting key `optimizer_model_id` in the existing `TenantSetting(tenant_id, key)` store for the **session tenant** (root tenant when multi-tenancy is off). A value, not a column; the setting row is never rewritten to normalise a stale value.
- Resolution (`get_optimizer_model_state`, never raises): explicit value set and resolvable in the tenant's catalogue and not `is_disabled` → `source="optimizer"`. Unset → resolve the authoring model via the existing `get_authoring_model_state` → `source="authoring"`. Explicit set but unusable → `optimizer_model_not_enabled` (no fallback). Unset and authoring unusable → `optimizer_model_not_configured`, echoing the authoring `reason_code`. `require_optimizer_model` raises `OptimizerModelNotConfigured(reason_code, message)`.
- Never falls back to `AgentType.model_id` (the subject's runtime model) or to a first-available config. No resolved model is persisted anywhere, and no fallback value is written back to the setting.
- Used at exactly two points: the internal agent-context response for an optimization conversation (AR builds the turn from identifiers), and the availability projection returned to the UI/tab.
- CC-only module; AR/CH must never import it (structural test).

### 9. System Config

- New "Optimizer Model" section alongside the authoring section, both workspace-scoped:
  - Explains that it powers the *optimization conversation and the plan work it does* (not a runtime model), that unset inherits the plan-authoring model, that the choice affects subsequent optimization in this workspace only, and that replay-only / single-use approval / the script lifecycle are unaffected by the choice.
  - Options come only from the session tenant's enabled, non-disabled catalogue. Unset renders an explicit "inherit the plan authoring model" option; a stale saved value renders as a disabled "no longer available" option with a re-select reminder and Save blocked until re-selected (same pattern as the authoring section).
  - A reminder when no usable model exists (nothing configured and no authoring model, or the resolved model is unavailable) with a pointer back to the section — matching the chat-side blocked state.

### 10. Frontend optimization chat surface

- Entry: the Optimized Plan tab (per agent type) gains a primary **Talk to optimizer** action annotated "runs as `<agent type>` — same identity and permissions", plus a blocked variant that explains the missing precondition and links to System Config. Success shows **both** the one-shot Optimize action (when the one-shot gate allows it) and this entry; the entry is available for typed **and** conversational agent types. The manual feedback box and retire action remain.
- The chat reuses `ConversationDialog`'s conversational experience (multi-turn context, working/waiting indicators, session controls, history/resume, reconnect recovery) in an **optimization mode** driven by the conversation `channel`/`sessionId`:
  - header: the agent type's name only (no "system-provided" chrome, no separate optimizer persona); the identity parity statement "Runs as this agent — same identity and permissions" is a **tooltip on the mode chip**, not a header block;
  - session bar: one compact, **default-collapsed** "What ran in this session" bar keeps the safety signal visible (N replay verifications · N approved live operations · replay-only/live chip) and expands to the full audit detail (identity, scope, last live time); it is the only chrome above the transcript, and business/assistant conversations render nothing;
  - model-unavailable alert with reminders and a System Config shortcut (composer disabled, no work started);
  - activity: the existing status stream plus expandable step/tool detail ("what it looked at") and terminal outcomes instead of an indefinite spinner;
  - ask card and script-based live-test approval card rendered inline; composer blocked while a decision is pending;
  - the approval card is expanded only while `pending`; once it leaves `pending` (approved/running/executed/failed/denied/expired/cancelled) it collapses into a one-line history summary (status chip + script name + short result/denial) that expands to the script run record.
- Plan refresh: a completed turn (or any change in the plan state for the subject) invalidates the `['agents','types',<id>,…]` query scope and, while a turn is in flight, polls the optimized-plan query so the tab updates without a reload.
- All text goes through `t()`; dialogs follow the Dialog Error Handling Standard (`dialogError` + `PermissionDeniedAlert`).

### 11. Availability & failure surfaces

| Condition | Chat surface | Backend |
|---|---|---|
| No usable optimizer model (nothing configured + no authoring model, or resolved model unavailable) | Model alert + System Config link; composer disabled; no work starts | `availability.reason_code` is `optimizer_model_not_configured` or `optimizer_model_not_enabled`; internal context `412 optimizer_model_unavailable` |
| No successful reference execution | Explanation of what is missing; work not started | `availability.reason_code = no_successful_execution` |
| No base/optimized plan yet (e.g. conversational agent) | Informational "nothing to optimize yet — I can start from your description"; conversation opens | `availability.plan_present = false` (not a block) |
| Agent type is conversational | Entry available (no longer blocked) | creation guard accepts it; only the one-shot action keeps its conversational precondition (`conversational_agent`) |
| Operator lacks permission | Entry disabled; API `403` | `require_permission` (`agent::read` to open, `agent::execute` to work) |
| Turn hang / failure | Structured outcome message, not an eternal spinner | existing heartbeat / per-call timeout / turn watchdog / iteration budget |
| Replay cannot prove the script, or the operator explicitly asks for a live verification | `needs_feedback` stop + "what is missing" + ask/decide or live-test request | terminal `needs_user_input` from `execute_script`; explicit request is a valid live-test reason |
| Live detection during the run fails (sandbox violation, cap, permission denial) | Failure shown; the script stops, replay-only restored | ledger `failed`, remaining script work not attempted |

## API Changes

All public endpoints are JWT-authenticated and tenant-scoped; all internal endpoints are mTLS + signed tenant headers (`internal_httpx_client` only). No endpoint gains a tenant-less path. **No endpoint accepts a scope/target agent type beyond the session**: the subject is the session's `agent_type_id` and is never re-supplied by a client after creation.

### Public REST (Control Center)

- `POST /conversations/optimization` (**new**) — open an optimization conversation on the subject agent type.
  - Request: `{ "agent_type_id": "<uuid>" }` (the subject; no scope parameter, no optimizer id).
  - Behavior: `404` unknown subject in the tenant; `403` lacking `agent::read` on the subject. Creates `ConversationSession(agent_type_id=<subject>, channel="optimization", triggered_by_user_id=<operator>, status=active)`. Typed and conversational agent types both accepted. Nothing else is written; no optimization work starts.
  - Response `201 OptimizationConversationRead`: `{ conversation: ConversationSessionRead, subject: { agent_type_id, name, input_type, is_conversational }, availability: { available, reason_code, reason, can_start_work, plan_present, optimized_plan_status, successful_executions, optimizer_model: { model_id, source, configured, enabled, reason_code } } }`.
- `GET /conversations/{session_id}/optimization` (**new**) — subject + availability + audit for an existing optimization conversation (`404` unknown, `403` not the owner/tenant, `422 not_optimization_conversation` when the session's channel is not `"optimization"`). Response adds `audit: { replay_verifications, live_operations, last_live_at, replay_only }` computed from the session's `RuntimeToolCall` rows (`system____execute_script` calls vs rows carrying `optimization_live_test_request_id`) and the ledger. Used on open, resume and reconnect.
- `GET /conversations/{session_id}/live-test-requests` (**new**) — ledger for the session, newest first: `id`, `status`, `target_agent_type_id`, `script_version_id`, `script_name`, `script_version_label`, `requested_operations` (tool-call preview), `executed_operations` (script run record), `expires_at`, `execution_started_at`, `execution_finished_at`, decision (`approval_value`, `operator_user_id`, `responded_at`), `created_at`. Powers the approval card, the audit block and the "what ran" review.
- Chat turns (existing `WS /ws/chat` + internal `prepare-turn` / `append-turn`, **unchanged transport**) — a message on an optimization session is dispatched to AR's conversational loop (contract 2). `POST /conversations/{session_id}/end` and `/archive` keep their behaviour.
- `GET /conversations/{session_id}/interventions/pending` (**unchanged shape, optimization-aware**) — returns the outstanding ask/decide (or live-test approval) request so the chat can re-surface it after reconnect or resume; for a live-test approval it includes the ledger id, `script_version_id`, `expires_at` and the script's tool-call preview. Empty list when nothing is pending; `404`/`403` checks unchanged.
- `POST /conversations/{session_id}/interventions/{request_id}/respond` (**changed behavior**) — unchanged request/response shape; when the intervention belongs to a live-test request it first runs the expiry check, then on `approval_value = true` consumes the approval once and runs the approved **script** once **before** dispatching the resume (the script run record is carried in the resume value); on `false`/absent it marks `denied` and dispatches the denial resume. A second response/decision returns the stored terminal outcome (`409` semantics preserved by the existing status check) and never re-executes.
- `GET /agents/model-configs/optimizer-model` (**new**) — `{ selected_model_id: string|null, effective_model_id: string|null, source: "optimizer"|"authoring"|null, configured: bool, enabled: bool, reason_code: string|null, options: [{model_id, config_id, config_display_name, provider_type}] }`. Options come only from the session tenant's enabled, non-disabled configs; `selected_model_id` echoes the raw stored value (a stale value stays visible).
- `PUT /agents/model-configs/optimizer-model` (**new**) — `{ "model_id": string|null }`; `422` when the id is not enabled in this workspace's catalogue; `null` clears (restore inherit-from-authoring). Requires `agent::update`. Writes only the session tenant's own `TenantSetting` row.
- `GET /agents/types/{type_id}/optimization-gate` (**extended, additive**) — adds `optimization_conversation_available: bool`, `optimization_conversation_reason_code: string|null`, `optimizer_model_configured: bool`, `optimizer_model_id: string|null`, `optimizer_model_source: "optimizer"|"authoring"|null`, `optimizer_model_reason_code: string|null`. Existing fields keep their meaning; `can_optimize` remains the **one-shot** precondition and is therefore still `false` for conversational agent types (the conversation entry uses `optimization_conversation_available`).
- `POST /agents/types/{type_id}/optimized-plan/retire`, `POST /agents/types/{type_id}/optimize-plan/feedback`, `POST /agents/sessions/optimize` — unchanged.

### Internal REST

- `GET /api/v1/internal/data/agent-types/{agent_type_id}/context?conv_session_id=…` (**changed**) — when `conv_session_id` resolves to an optimization session: return the **optimizer model** `model_id` / `model_config_id` (never the agent runtime model), the composed optimization mission as `system_instruction`, the optimization tool set including `request_live_test`, the `optimization` block, no business tools, and no typed output schema. Resolution failure → `412 {detail:{error:"optimizer_model_unavailable", reason_code, reason}}` (fail closed). A `conv_session_id` that is not an optimization session, and every existing caller without it, keep today's behaviour. Identifiers only.
- `POST /internal/conversation/turn` and `/internal/conversation/resume` (**caller change only**) — AR passes `conv_session_id` into `get_agent_context` so the mode is resolved for the turn and for any resumed turn. Transport, pause and checkpoint semantics unchanged.
- `POST /conversations/{conv_session_id}/prepare-turn` (**changed**) — persists the user turn exactly as today, then returns `optimization: { mode, subject_agent_type_id, available, reason_code, reason }` alongside `no_agent_message`. The mission lives in the agent context, so no scope-instruction composition is added here.
- `POST /api/v1/internal/system-tools/request-live-test` (**new system tool**) — body `SystemToolRequest` with `conversation_session_id`, `agent_type_id` (the subject, validated against the session) and args `{ script_version_id: string, reason: string }`. **No operation list**: the optimizer saves the script first (`generate_script`), and the tool-call preview is derived server-side from that version's `python_source` (`extract_tools_call_names`).
  - Validates subject match, that the version exists in the conversation's tenant, has `python_source` and belongs to the subject agent type, that the script has literal `tools.call` names, and that the preview is within the subject's own grants; bounds are one pending request + the per-session approved cap + the decision TTL.
  - Refusals return `{"status":"refused", "reason_code": …, "reason": …}` and write nothing: `out_of_scope`, `invalid_script_version`, `script_version_not_found`, `no_tool_calls`, `operation_not_permitted`, `live_test_already_pending`, `live_test_quota_exhausted`.
  - Accepted → creates `OptimizationLiveTestRequest(status=pending, target_agent_type_id=<session subject>, script_version_id=<version>, requested_operations=<tool-call preview>, expires_at=…)` + `InterveneRequest(intervention_type="approval", conversation_session_id, reason=<rendered card>)` in one transaction, links `request_turn_id`/`intervene_request_id`, returns `{"status":"pending", "live_test_request_id", "intervene_request_id", "expires_at", "script_version_id", "operations":[preview]}`.
  - The approval card text is titled **"Run this script live"** and carries the script name/version, the preview ("it will call: …"), "runs once as this agent; MCP tools are assumed to work", the expiry, and the single-use rule; denial/expiry leaves the session replay-only.
- The live-test execution has **no public entry point and no self-service trigger**: it is initiated only by CC's answer path (`turn_resolution.execute_approved_live_test` → ledger `begin_execution` → load the approved version's `python_source` + reference input → `CommHubClient.forward_live_test`), which re-checks tenant, `status`, `expires_at` and the linked resume marker before forwarding. AR and CH expose only the internal run endpoint that accepts an already-authorized script; neither can originate a live test.
- `POST /internal/live-test/run` (Communication Hub, **new**) — CC → CH forward: `{ live_test_request_id, conversation_session_id, target_agent_type_id, script_version_id, script_name, script_version_label, python_source, input_context }`, returns `{ status: "executed"|"failed", executed_operations: [script_run], started_at, finished_at, error }`. Transport only; CH adds no authorization of its own beyond its existing control-plane checks and forwards with `internal_httpx_client`.
- `POST /internal/live-test/run` (Agent Runtime, **new**) — executes the approved **script once** in the real sandbox with the live session-bound `CommHubToolClient` (`provenance="live_test"`): fetch the subject agent type's context (`agent_type_id` only, unscoped) for capability, verify the script's statically extracted `tools.call` names are all in that allowed set (a denied name starts no work), then run `ScriptRunner.execute_python_source(python_source, session_id=conversation_session_id, agent_type_id=target_agent_type_id, initial_context=<reference input>, tool_calls_out=…)` under a hard per-run wall clock. The script's own `tools.call(...)` is the only egress — identity injected by CH per call (the agent's own identity, no override). On a sandbox violation, cap termination or tool error: stop, do not retry. Every `tools.call` is recorded as a `RuntimeToolCall` with `session_kind="conversation"`, `session_id=conversation_session_id` and `optimization_live_test_request_id`. No LLM is involved. Returns one `{kind: "script_run", …, tool_calls[], telemetry}` record.
- `POST /api/v1/internal/session-data/tool-calls` (**changed**) — `RuntimeToolCallRecord` gains optional `optimization_live_test_request_id`; persisted on the row. Absent for every ordinary run, replay verification and normal conversation turn.
- `POST /api/v1/internal/system-tools/get-execution-log`, `execute-script`, `generate-optimized-plan`, `generate-script`, `get-*` (**changed guard only**) — every handler that takes `agent_type_id` first applies `require_subject_match` for an optimization session; an out-of-scope request returns the structured `out_of_scope` payload and writes nothing. Replay semantics, bounds and allow-lists are otherwise unchanged.
- `GET /agents/model-configs/workflow-generation` / `PUT` — unchanged.

### WebSocket (chat)

- `intervene_request` server message gains an optional `live_test` block for live-test approvals: `{ live_test_request_id, status, expires_at, script_version_id, script_name, script_version_label, operations: [tool-call preview] }`. Plain ask/decide messages are unchanged.

## Data Access Patterns

Control Center is the only database writer; Agent Runtime and Communication Hub receive the mode, authorization and identifiers through the existing mTLS internal APIs (never direct DB access).

- **No seeding and no start-up writes** — optimization needs no `AgentType` row, no identity/role/skill binding, and no per-tenant settings row. A tenant gains the capability with no data step.
- **Conversation create (write, CC only)** — one `ConversationSession` row: `agent_type_id` = subject, `channel = "optimization"`, `triggered_by_user_id`, `status`. No other write, and no availability/model value is persisted.
- **Mode read (read, session-scoped)** — `resolve_optimization_mode(db, conv_session_id)` loads the session once per turn/tool call and exposes `(tenant_id, agent_type_id, channel, triggered_by_user_id)`; the mode check is `channel == "optimization"`. `require_subject_match` compares the requested `agent_type_id` with the session's; absent session id keeps legacy behaviour. All ORM reads use the tenant-scoped session (no hand-written tenant filter, no raw client).
- **Optimizer model resolution (read, tenant-scoped)** — `TenantSetting(tenant_id, "optimizer_model_id")` for the session tenant → `ModelBindingLayer.resolve_model_config` on the tenant-scoped session; unset → the existing authoring resolver. Configured/enabled/disabled are **derived at read time**; the setting row is never rewritten. No fallback to the agent runtime model.
- **Availability (read-only, computed)** — composed from the subject's execution/plan state, the optimizer model state, and the subject's permission checks. Nothing stored; the chat gate and every server check recompute it so UI and server agree.
- **Conversation + turns (write, CC only)** — `prepare-turn` persists the user turn + `thinking` activity as today; `append-turn` persists the agent turn, status events, guardrail usage and resolves the terminal activity. `agent_type_id` and `channel` are never updated after creation (no update path exposes them).
- **Pause / resume (write, CC only)** — unchanged: `InterveneRequest` (+ response) → `ConversationTurnResume` (`idempotency_key`, `write_applied`, claim, expiry) → exactly one dispatch. The optimization path only adds the ledger link (`resume_id`, `intervene_request_id`) and the domain status projection.
- **Ledger (write, CC only)** — create on request (subject derived from the session, script version proven to belong to the subject, preview derived from the source); conditional transition on execution start (single-shot); the script run record written once from the run result; denial/expiry/cancel terminal writes; expiry sweep at startup + periodically, with a lazy `expires_at` check on decision.
- **Live execution (no DB in AR/CH)** — CC → CH → AR with the approved script version's `python_source` and the reference input; AR runs that script once in the sandbox and calls CH's tool route per `tools.call`; tool-call records are ingested back to CC with the ledger pointer. No operation list crosses the boundary and nothing is executed tool-by-tool. Persisted script source/arguments are state context only and never contain tokens, credentials or decrypted secrets.
- **Audit reads (read)** — ledger by conversation (tenant + owner scoped), session audit counts from `RuntimeToolCall` (`execute_script` replay calls vs rows with a ledger pointer), plan state from `OptimizedImplementationPlan` (unchanged read path). Replay evidence remains `VerificationRun` / `ScriptExecutionRecord`.
- **Plan outcome (write, unchanged path)** — the optimizer persists through `generate_optimized_plan` (`ready` / `needs_feedback` / `failed` allow-list) exactly like the one-shot command; nothing bypasses verification because it happened in chat, and the conversation never writes plan rows directly.
- **System Config (read/write, tenant-scoped)** — `GET/PUT /agents/model-configs/optimizer-model` list only the session tenant's enabled catalogue and write only the session tenant's `TenantSetting` row; a stale selection stays visible and is never auto-cleared.
- **Migration (two revisions)** — `3d7c2a5940bc`: new `optimization_live_tests` table + enum and the nullable `runtime_tool_calls.optimization_live_test_request_id`; `7b1e4c2d9f03` (child): nullable `optimization_live_tests.script_version_id` FK. No `conversation_sessions` change, no backfill, no column drop.

## Invariants to preserve

- Three segregated services; only CC touches PostgreSQL; only AR executes turns, replay and live operations; CH is the only holder of identity material (injected per call).
- **No new agent identity, agent type, role or permission.** Optimization acts with exactly the subject agent type's identity, role and grants, and never broader.
- Replay-only remains the default verification path; `execute_script` never contacts a live integration.
- Normal business runs are unaffected: business instructions, skills, granted tools and routing are unchanged outside an optimization conversation, and no mode survives it.
- Plan lifecycle, verification rules, retire behaviour, execution preference/fallback, requires-fix marking, script registry/sandbox rules, tool-permission semantics and tenant-isolation mechanics are unchanged.
- No automatic/unattended re-optimization, no "always allow live", no remembered approval, no deletion, no credential handling, no cross-agent reach.
- The one-shot Optimize action and the manual feedback path keep working exactly as before.
