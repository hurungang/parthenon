# Tech Spec: Agent Management Panel

## Technical Overview

A frontend-only composition feature: a new unified Agent Management Panel (route `/agents/panel`) where an administrator configures an agent — role, identity, skills, SOPs, input/output data types, model — from a single three-region layout (agent list, live topology, property bar). The right property bar is the single editing surface for ALL agent properties: a "Properties" section edits every base property (name, description, system instruction, execution guardrails) and the equipment slots below it edit the equipped resources. Agent creation keeps a dedicated dialog hosting the shared `AgentTypeForm`; there is no edit dialog — editing an existing agent happens exclusively in the property bar. The six existing module dialogs are relocated into shared components and mounted by the panel through a shared dialog host, so inline creation is behaviourally identical to the source modules (PRD hard requirement) with zero duplication. All panel edits mutate a client-side draft composition state; a single save maps the draft onto the existing agent-type update endpoint. The live topology is composed client-side from the draft — including a static Communication Hub platform node — so it updates before saving without any runtime calls to the Communication Hub service. No database, permission-model, or inter-service changes; the three-service segregation and Control-Center-only database access are untouched. One targeted backend hardening accompanies the panel (same Control Center service, no schema change): the agent-type create/update endpoints commit before scheduling background plan regeneration and map binding-write unique-constraint collisions to a structured 409 with per-binding detail (see "Save flow race-safety" below).

Typing conventions: all new state and contracts are TypeScript interfaces/enums (draft composition, slot definitions, create-and-assign results) added to the shared types module; no inferred `any`. All UI text resolves through i18next `t()` with keys in the English locale file.

### Permission gating

No new resource types and no permission-resolution changes — each equipment slot declares its existing manifest entry in `EQUIPMENT_SLOT_DEFINITIONS`: `agent::roles`, `agent::identities`, `agent::skills`, `agent::sops`, `agent::data_types`, `agent::model_configs` (agent CRUD actions have no explicit binding and degrade through the standard API error surfaces). The backend authorization engine remains authoritative. Client-side, the panel follows the established graceful-degradation pattern: a 403 on a slot's list query disables that slot's actions with an explanatory localized note instead of an error, and structured 403 responses are parsed and surfaced through `PermissionDeniedAlert` in-dialog and the global permission snackbar. A user with read-only access can browse and review compositions; write actions are disabled with an explanation.

## State Management

All new state is local React state via hooks; no new global store.

- **Draft composition state** — the core concept, owned by `useAgentDraftComposition`: a typed in-memory copy of the selected agent covering base properties (name, description, system instruction, execution guardrails) and equipment (identity, role, skills with binding order, SOPs with binding order, input type/schema, output data type, model). Initialized from the fetched `AgentType` when an agent is selected. Every assign/unassign/inline-create/property-edit mutates the draft only and marks it dirty — no API calls until Save. Save maps the draft onto the existing agent-type update payload (one PUT), rejecting an empty or non-slug name before any call; the payload's binding lists are deduplicated by resource id (a skill both directly bound and composed under a SOP appears once — first occurrence wins for order) and the write is single-attempt with an in-flight guard so a slow save is never overlapped or retried; Discard reverts to the last snapshot. The dirty flag (plus a dedicated base-properties-changed flag and a name-validity flag) drives the `PendingChangesTray` and the unsaved-changes guard (`useUnsavedChangesDialog`) on agent switch and navigation.
- **Agent selection state** — the selected agent id, held by `AgentManagementPanelPage`; changing selection refetches the target agent, resets the draft from fetched data (guarded by the unsaved-changes dialog), and re-renders the topology.
- **Dialog host state** — which shared dialog is open and its mode/create-and-assign target, held by the panel page and passed to `SharedDialogHost`; only one dialog is mounted at a time. Dialog-internal state (field values, saving flags, `dialogError`) remains inside each dialog, per the Dialog Error Handling Standard.
- **Assign-existing picker state** — `pickerSlot` registers which slot's `ResourcePickerDialog` is open (one at a time) and `pickerPresetIds` carries an inline-created resource so the refreshed picker list pre-selects it; while the picker is open for a slot, `SharedDialogHost` create completions for that slot route to the preset instead of direct draft assignment, and the picker's Assign button applies the confirmed selection to the draft (draft-only, persisted by the single panel save). The picker stays mounted behind a create-new module dialog, completing the "find or create" journey in one place; the shared dialog host still mounts exactly one module dialog at a time.
- **Server cache** — react-query owns all server data. Inline create-and-assign relies on the dialogs' existing mutations and query invalidations (their own list caches refresh), and the panel additionally invalidates the agent-types and affected list queries after draft save so the sidebar and any open views reflect saved state immediately.

## Data Access Patterns

- **react-query for all server data.** The panel reuses the existing data hooks where they exist — `useAgentTypes` (agent list/detail), `useDataTypes` (data type registry), `useAvailableModels` (flattened enabled models) — and uses inline `useQuery` calls mirroring the source list pages for roles, identities, skills, and SOPs (those lists are fetched inline today, so the panel mirrors the established pattern rather than inventing new hooks). All calls go through `apiClient` with JWT injection; 401/403 handling is centralized in its interceptors.
- **Client-side topology composition.** The live topology is derived purely in the browser from the draft composition (via `buildPanelTopology`), not fetched: (a) it must re-render instantly on every pre-save change, which server data cannot reflect; (b) the Communication Hub is a fixed platform node (broker · agent gateway · MCP), so no runtime query against the Communication Hub service is needed — consistent with the segregation rules; (c) it works identically for unsaved drafts, saved agents, and brand-new agents. The one read-side enrichment is the bound SOPs' details (`GET /sops/{id}` — react-query key `['sops', 'details', sopIds]`, deduplicated with `AgentTypeDetailsDialog`), which source each SOP's `skill_invocation` steps for the SOP → composed-skill → tool chain; while those details load the SOP nodes render without their chain, and no draft mutation ever triggers a request (the query key changes only when the SOP bindings themselves change).
- **Client-side filtering** for the agent list sidebar (search/filter over the fetched list), matching the existing module pages' approach, and for the assign-existing `ResourcePickerDialog` (debounced search + client-side pagination over the full fetched list via `usePagination` — no new server endpoints as resource counts grow).
- **Single-write save.** Equipment changes accumulate in the draft; saving issues exactly one agent-type update call, avoiding partial configurations. Inline resource creation is the only immediate write, because those resources must exist server-side before they can be referenced — that is the dialogs' own existing behaviour, unchanged.
- **Save flow race-safety.** The PUT payload deduplicates binding lists by resource id (first occurrence wins for order — `useAgentDraftComposition`), the save never overlaps itself (in-flight guard; retries are disabled for this write), and the backend is idempotent for resubmits: `AgentTypeService.set_bindings` dedupes incoming lists and bulk delete-then-inserts, the create/update endpoints commit before scheduling the background plan regeneration (so the tens-of-seconds LLM task never runs against an uncommitted binding write), and a residual unique-constraint collision (genuinely concurrent saves) returns a structured 409 `binding_conflict` with per-binding detail instead of a raw 500. Binding-validation failures return 422 `binding_validation_failed` with both a backwards-compatible `messages` list and a structured `errors` array (`resource_type`/`resource_id`/`rule`/`message` — Pydantic `BindingError` models); each error is also logged individually. The `PendingChangesTray` renders each structured binding error (title + per-error list) and falls back to the generic error alert only when no detail exists.
- **Graceful permission degradation.** Read failures (403) on any list disable the corresponding slot actions with an explanation; structured 403 bodies are parsed and rendered by `PermissionDeniedAlert` / the global permission snackbar. The server remains the single enforcement point.
