Platform Design

High-Level Architecture

Parthenon is composed of three strictly isolated backend services and a dual-identity model, connected through a permissions framework built around Skills, SOPs, and Agent Roles.

🔌
SOP / Skill-Driven MCP Integration
  • Skills wrap one or more MCP tool calls into a named, permissionable unit
  • SOPs (Standard Operating Procedures) compose multiple Skills with sequencing logic and support agent-to-agent delegation
  • Each MCP server is registered with a unique slug; all its tools are synced under that namespace
  • Permissions are granted at the tool level — agents only see the tools their assigned Skills allow
🛡️
Security & Permission Control
  • Agent Roles are permission sets granting access to specific SOPs and Skills
  • Roles resolve to a complete, deterministic set of allowed MCP tools at execution time
  • Agent identities are first-class OIDC principals in a dedicated agent realm, never sharing human credentials
  • Agents never hold identity tokens directly — tokens are injected per tool call by the Communication Hub
⚙️
Three-Service Isolation
  • Control Center — sole database owner; manages CA, issues certificates, resolves permissions, maintains audit logs
  • Communication Hub — central broker for UI↔agent and agent↔agent messaging; acts as Agent Gateway for session management
  • Agent Runtime — the only service that executes agents (LangChain deep loop); authenticates via mTLS, never touches the database
  • Cross-service calls use certificate-based mTLS; no service shares database credentials
🪪
Dual Identity Support
  • User Realm — human accounts; OIDC login via Keycloak or Azure EntraID; standard OAuth2 flows
  • Agent Realm — dedicated OIDC realm for AI agent identities; credentials stored encrypted, refreshed automatically
  • Agent Types define the pairing of an agent identity, role, model config, system instruction, and I/O type
  • Each execution validates that the agent identity is still assigned to its declared role before proceeding

Trust & Compliance

Security Deep Dive

Parthenon enforces security at every boundary — from tool-level permissions to certificate-based service identity and strict token isolation.

🔐
Tool-Level Permission Control

Permissions are granted at the individual MCP tool level, not at the server level. Agent Roles define which Skills an agent can invoke; at runtime, those Skills resolve to an exact, deterministic allow-list of tools. Agents cannot call any tool outside that computed set — enforced by Control Center on every request.

SOP → Skill → Tool
📜
mTLS Certificate Authentication

Each Agent Runtime instance receives a short-lived agent-instance certificate (24-hour validity) issued by Control Center's built-in Certificate Authority. Internal services such as the Communication Hub use longer-lived service certificates (30-day validity). All inter-service calls are mutually authenticated via mTLS — no shared secrets or API keys cross service boundaries.

24h agent-instance · 30d service
🔒
Token Isolation

Agent Runtime instances never hold identity tokens. When an agent needs to call an MCP tool, the Communication Hub resolves the correct OIDC token for the agent identity and injects it into that specific tool call — just-in-time and scoped. Agent-instance certificates are explicitly blocked from internal management endpoints, ensuring runtime agents cannot access certificate management or raw credential stores even if compromised.

Step-by-Step Walkthroughs

Demo Walkthroughs

Follow these guided flows to understand how operators configure and run AI agents on the Parthenon platform.

  1. 1

    Register the MCP Server

    In Control Center → MCP Hub, click Add MCP Server. Supply a unique slug (used as the tool namespace), the server URL, and any authentication credentials. Credentials are encrypted at rest and decrypted only at call time.

  2. 2

    Sync & Verify Tools

    Click Sync Tools. Parthenon queries the MCP server's manifest and imports all available tools under the server's slug namespace. Review the synced tool list to confirm all expected tools are present.

  3. 3

    Configure MCP Sessions

    Create one or more named sessions for the server — each session can bind different identity credentials (an agent identity or a role). Sessions allow the same physical server to be called with different OIDC contexts.

  4. 4

    Test Connectivity

    Use the built-in connection test to confirm the server responds correctly and the tool manifest is accessible. A green status indicator confirms the server is ready to be referenced in Skills.

  1. 1

    Define a Skill

    In Control Center → Skills, click New Skill. Give it a descriptive name and select which MCP tools it wraps. A Skill is the smallest permissionable unit — granting access to a Skill grants access to exactly the tools it declares.

  2. 2

    Compose an SOP

    In Control Center → SOPs, create a Standard Operating Procedure by composing multiple Skills in sequence. Add branching logic or agent-to-agent delegation steps as needed. SOPs represent higher-level, reusable business workflows.

  3. 3

    Review the Tool Allow-List

    The platform automatically resolves which MCP tools the SOP will expose at runtime. Review the computed allow-list to confirm it matches your security intent before attaching the SOP to any Agent Role.

  4. 4

    Test the SOP in Isolation

    Use the SOP test runner to simulate execution with a mock agent identity. Observe which tools are called, in what order, and inspect intermediate outputs before exposing the SOP to production agents.

  1. 1

    Create an Agent Role

    In Control Center → Agent Roles, click New Role. Select the SOPs and Skills this role grants access to. The platform immediately computes and displays the complete, transitive set of MCP tools that will be accessible to any agent assigned to this role.

  2. 2

    Assign Agent Identities

    Attach one or more Agent Identities (OIDC principals from the agent realm) to the role via the many-to-many assignment panel. An agent identity can hold multiple roles; each execution validates the assignment is still active before the agent loop begins.

  3. 3

    Audit the Role

    Review the audit trail showing when the role was created, which identities are assigned, and the last time permissions were resolved. All changes are logged in the Control Center audit log for compliance.

Agent Types define an agent's identity, role, model configuration, system instruction, and I/O type. Once saved, an LLM automatically generates a step-by-step execution plan displayed in a preview modal with a visual topology diagram. Agents can be triggered in two distinct modes:

⚡ Non-Conversational Trigger
  1. 1

    Define the Agent Type

    Set I/O type to Non-Conversational. Supply a structured input schema and a system instruction. Attach the Agent Identity and Role.

  2. 2

    Trigger via Schedule or API

    Use the scheduler (cron) or call the Agent Gateway API directly with the structured input payload. The Communication Hub dispatches the job to an Agent Runtime instance.

  3. 3

    Retrieve Structured Result

    The agent persists its final output using the platform's built-in result-persistence tool. Query the Result Repository for structured output, or subscribe to the completion notification channel.

💬 Conversational Session
  1. 1

    Define the Agent Type

    Set I/O type to Conversational. The agent maintains conversation history across turns — every interaction is persisted to the conversation store for audit and replay.

  2. 2

    Open a Session

    The Web UI opens a real-time WebSocket session via the Communication Hub. Send the initial user message; the Hub dispatches the job and streams agent responses back to the browser.

  3. 3

    Continue the Conversation

    Subsequent messages are appended to the session history. The agent's LangChain observe-reason-act loop runs for each turn, with full tool call tracing visible in Execution Logs.

Every agent run produces a rich, structured execution log visible in the Execution Log Viewer on the Agent Session page. Logs are captured before the first LLM call and span the entire observe-reason-act loop.

  • System context snapshot — full system instruction and user prompt captured at submission time for audit and traceability
  • Span-based hierarchy — iterations, LLM calls, tool calls, and agent-to-agent delegations are grouped into collapsible spans with timestamps and icons
  • Tool call details — each MCP tool call shows the input payload, raw response, and duration; expandable inline
  • Raw log toggle — switch between the structured user-friendly view and the raw technical log for debugging
  • OTEL integration — traces, metrics, and structured logs are emitted to the configured observability backend (Prometheus, Jaeger, Loki, etc.)
