## New Capabilities

- **Tenancy Mode Switch** — platform-level enable/disable for multi-tenancy; disabled by default so single-tenant behavior (local dev, demos, self-hosted) is unchanged. With multi-tenancy disabled, everything defaults to the root tenant: the deployment behaves exactly like the root tenant's workspace.
- **Root Tenant Platform Model** — the platform itself is a tenant: the internal system tenant becomes the **root tenant** (workspace address/name: `root`). Platform staff are simply members of the root tenant holding platform roles. All common modules (permissions, identity-provider configuration, member management) are shared by every tenant, including root. Platform modules are visible and accessible only to root-tenant members holding platform roles, after signing into the root workspace. Enabling multi-tenancy on an existing deployment adopts it as the root tenant.
- **Tenant Admin Module** — a tenant-scoped administration module present in every tenant workspace (alias/display name, identity-provider configuration, member management), in addition to the standard workspace modules. Normal tenant users — including the tenant root and delegated admins — see only tenant modules (standard modules + tenant admin module) and never platform modules.
- **Permission Containment** — every permission grant, including wildcard grants covering "all resources, all actions", applies strictly within the session's tenant. No global or cross-tenant roles exist: a root-tenant platform role grants platform modules and nothing in any other tenant; a tenant role grants nothing in the platform. Enforced centrally and backed by automated containment tests.
- **Unified Sign-In** — one login flow for everyone: enter a workspace address (e.g. `test-com` or `root`), then sign in via that tenant's OIDC provider or a platform-issued email + password. Signing into `root` with a platform role opens the platform console. There is no separate platform login page; the previous discreet "platform admin sign-in" expansion on the tenant login page is removed; the super-admin break-glass remains available at the root workspace sign-in. One session = one tenant: a user with memberships in multiple tenants signs into each separately.
- **Self-Serve Tenant Registration (primary path)** — a visitor signs up with a personal email + password account; on success their tenant workspace is created instantly and they become its tenant root user — no platform-admin involvement. A user who already owns a tenant is blocked from registering again with a clear message; the limit is one owned tenant per user (may be raised later). Platform-admin tenant creation remains available as a secondary, administrative path (the designated primary contact becomes that tenant's root).
- **Tenant Root User** — permanent tenant super-admin with ALL permissions inside the tenant. Root role/membership is immutable: it cannot be changed, demoted, or removed by anyone — not by other tenant admins, not by platform admins; violations are rejected and audited. The root can update the tenant alias (display name); the unique tenant address stays fixed.
- **License & Tier Management** — platform admin assigns each tenant a license defining a tier (free / team / enterprise) with limits: maximum users, maximum agent types, and monthly agent executions. A tenant without an assigned license automatically runs on the free tier with lower default limits. License changes take effect immediately.
- **Tier Quota Enforcement** — when a tenant reaches a limit, the corresponding action (inviting/creating users, creating agent types, submitting agent executions) is blocked with actionable feedback naming the tier, the limit, current usage, and the upgrade path (contact the platform admin to change tier). Agent executions are counted per calendar month per tenant and reset at the start of each calendar month. Tenants see their tier, limits, and current usage at a glance; usage reporting must match actual tenant records.
- **Tenant Registry & Lifecycle** — tenants with a unique name and unique tenant web address; created via self-serve registration (primary) or by platform admin; guided onboarding; suspend/resume; delete with full data removal and address reuse.
- **Tenant Address Resolution** — the tenant web address alone determines the workspace a visitor lands in; one session is bound to exactly one tenant (including the root tenant); users in multiple organizations choose at sign-in and re-authenticate to switch.
- **Per-Tenant Identity Provider** — each tenant registers its own OIDC provider independently; a single provider configuration may also be shared, serving the root workspace sign-in and multiple tenants at once with the workspace address deciding the session's tenant. Sessions are tenant-bound: a session created at one tenant's workspace address is invalid everywhere outside that tenant. Every identity is either self-managed (platform-issued email + password, independent of any OIDC provider) or linked to an external IdP identity.
- **Workspace Sign-In & Tenant Admission** — everyone signs in through the same unified flow at a workspace address (requires an active membership with a role in that tenant, root tenant included); the address alone binds the session to one tenant. Non-members are rejected cleanly with a clear "no access to this workspace" message — never a redirect loop.
- **First-Sign-In Auto-Onboarding (JIT Default Role)** — each OIDC provider configuration carries a configurable default tenant role chosen from the seeded presets (Tenant System Admin / Agent Manager / Agent Executor / Agent Viewer). A user's first OIDC sign-in to a tenant (no existing membership) creates the membership automatically with exactly that role; if unset, the first-time visitor is rejected like any non-member. Existing memberships and roles are never altered by sign-in; default-role changes affect only future first-time sign-ins.
- **Tenant Onboarding & Invitations** — guided first-run setup per tenant (connect sign-in, invite users, assign tenant roles); invite-based user onboarding; invitations respect the tenant's user quota.
- **Platform Admin Console** — platform modules, available only to root-tenant members holding platform roles after signing into the root workspace: tenant overview (status, tier/limits, created date, admin contact, usage counts), lifecycle actions, license assignment, and cross-tenant attempt audit; explicitly no browsing of tenant business data and no ability to alter a tenant root.
- **Tenant-Scoped Audit** — audit trails and security events carry tenant attribution; cross-tenant access attempts, root-protection violations, and quota-exceeded events are recorded and visible to platform admin.

## Modified Capabilities

- **Authentication & Sign-In**
  - Before: one deployment uses one identity configuration (bundled Keycloak or a single external OIDC provider) managed via System Config; super admin bootstraps access; every user signs in via that single provider; there is no concept of sign-in context or tenant admission — access is governed solely by roles granted in advance.
  - After: unchanged when tenancy is disabled. When enabled: **one unified sign-in flow for everyone** — the user enters a workspace address (`test-com`, `root`) and signs in via that tenant's OIDC provider or a platform-issued email + password (used by registering owners and self-managed identities). There is no separate platform login page; the discreet "platform admin sign-in" expansion on the tenant sign-in page is removed, and the super-admin break-glass remains available at the root workspace sign-in. The workspace address alone binds the session to exactly one tenant: signing into `root` with a platform role opens the platform console; a customer workspace address requires an active membership with a role there — non-members are rejected cleanly ("no access to this workspace"), never trapped in a redirect loop. A user with memberships in several tenants signs into each separately. One provider configuration can be shared across the root workspace and multiple tenants. Sessions are tenant-bound and rejected outside their tenant. Additionally, each provider configuration carries an optional default tenant role (seeded presets only): a first-time OIDC sign-in to a tenant auto-creates the membership with that role, while an unset default leaves the tenant invitation-only; existing memberships are never modified at sign-in.
- **Tenant Membership Model**
  - Before: (single-tenant product) administrators are regular users holding admin roles; any higher authority can grant, change, or revoke any administrator, and there is no tenant-owner concept.
  - After: unchanged when disabled. When enabled: every tenant has exactly one **tenant root** — the registering owner (or the primary contact designated at platform-admin creation) — holding ALL tenant permissions permanently. Root membership cannot be changed, demoted, or removed by other tenant admins or platform admins. Delegated tenant admins manage all other members, roles, and invitations, but never the root. Only the root can update the tenant alias (display name). A user account can own at most one tenant; a second registration attempt is rejected with a clear message.
- **Roles & Permissions (RBAC)**
  - Before: permission sets and the resource-type manifest are platform-wide; wildcard grants apply across the whole deployment.
  - After: unchanged when disabled. When enabled: roles, permission assignments, and resource-type policies are owned by a tenant and evaluated strictly within it — every grant, including wildcards such as `*::*`, applies only within the session's tenant; role names may repeat across tenants without collision; new tenant-management and license-management resource types cover platform-admin actions, granted only by platform roles in the root tenant.
- **Agent Management (types, identities, execution, sessions, logs)**
  - Before: agents and agent identities are platform-wide; identities provisioned in the dedicated agent realm; agent-type creation and execution submission are always available.
  - After: unchanged when disabled. When enabled: every agent type, identity, session, and execution log belongs to one tenant; agents execute strictly within their tenant's skills and permissions; agent-to-agent messaging cannot cross tenants; agent-type creation and execution submission are gated by the tenant's tier quotas (max agent types; monthly executions per calendar month per tenant).
- **MCP Hub**
  - Before: server slug unique platform-wide; tools synced under the slug namespace; sessions and credential bindings are platform-wide.
  - After: unchanged when disabled. When enabled: hubs, slugs, sessions, and credential bindings are tenant-owned; slug uniqueness is enforced per tenant; tool permissions are evaluated within the tenant.
- **Skills & SOPs**
  - Before: platform-wide definitions and permission grants; SOPs may delegate across all agents.
  - After: unchanged when disabled. When enabled: tenant-owned definitions; permissions grantable only within the owning tenant; delegation cannot leave the tenant.
- **Scheduling**
  - Before: cron schedules and execution history are platform-wide.
  - After: unchanged when disabled. When enabled: schedules and history are tenant-owned; a schedule can only trigger tenant-owned agents/SOPs; schedule-triggered executions count toward the tenant's monthly execution quota.
- **Model Configurations**
  - Before: centrally managed LLM provider configs shared by the deployment.
  - After: unchanged when disabled. When enabled: tenant-owned; each tenant manages its own provider credentials and enabled model lists.
- **API Keys**
  - Before: keys hashed and bound to agent identity and role, valid platform-wide.
  - After: unchanged when disabled. When enabled: keys additionally bound to one tenant and valid only for that tenant's resources.
- **Conversations, Outputs & Saved Data**
  - Before: persisted platform-wide; browsable by permitted users.
  - After: unchanged when disabled. When enabled: tenant-owned; only the owning tenant's members and agents can read, replay, or export them.
- **User & Tenant Administration Surfaces**
  - Before: System Config UI manages identity providers and platform settings for the single deployment; super admin is the bootstrap administrator; user management has no tenancy, licensing, or quota concepts.
  - After: split into platform-level administration (platform modules, reachable only from the root workspace by root-tenant members with platform roles: tenancy switch, tenant registry, license assignment, quota monitoring) and tenant-level administration (the **tenant admin module** available in every tenant workspace — tenant display name/alias, identity-provider configuration, member management within quota); normal tenant users, including the tenant root/admin, see only tenant modules (standard workspace modules + tenant admin module) and never platform modules; super admin extends into platform roles held in the root tenant; tenant admin surfaces show tier, limits, and usage, and block quota-exhausted actions with the tier/limit/usage/upgrade feedback.
- **Internal Service Boundaries (Communication Hub, Agent Gateway, Agent Runtime)**
  - Before: mTLS/certificate-based service identity; Control Center resolves permissions; internal allowlists protect boundaries.
  - After: tenant context travels with every verified internal request; Control Center remains the single tenant-enforcement and quota-counting point; internal services and agents can never widen the tenant context they receive.

## Removed Capabilities

- The discreet "platform admin sign-in" expansion on the tenant login page (when present) — replaced by the unified workspace-address sign-in; platform operations happen from the root workspace.
- Platform-wide (cross-tenant) permission scope, including global wildcard grants — all permission grants become strictly tenant-contained.

Otherwise multi-tenancy is additive and disabled by default; all existing single-tenant capabilities are preserved (with the deployment defaulting to the root tenant).
