Multi-Tenant Support — UI Prototype

Clickable flows for the hosted (SaaS) multi-tenancy epic. All data is placeholder — no backend calls.
💡Start where a real operator would: multi-tenancy ships disabled by default. Open Platform Admin and flip the switch in Platform Settings — the whole console changes. Then try the self-serve sign-up (instant workspace as tenant root), onboarding, sign-in, license quotas, and the isolation demo.
Platform Admin

1 · Tenancy Switch, Governance & Licenses

Platform Settings with the default-off multi-tenancy toggle and its irreversibility warning. Tenant list with create / suspend / resume / delete. Tenant detail gains license assignment (tier + limits) and usage columns — metadata only, business data never exposed.

Prospective Owner

2 · Self-Serve Sign-Up → Tenant Root

Visitor signs up with a personal email + password and an organization name — an instant tenant workspace, with the creator as its permanent tenant root. Includes the one-tenant-per-user block for accounts that already own a workspace.

Tenant Root

3 · Guided Onboarding Wizard

First-run setup for the new tenant root: connect the organization's own OIDC provider (issuer URL, client id/secret), invite users with roles within quota, and confirm the default workspace.

Tenant User

4 · Tenant-Branded Sign-In & Org Choice

One unified flow for everyone: sign-in opens on an AWS-style Find your workspace step — enter your workspace address (optionally remembered on this device; the platform itself lives at the root workspace) — then the workspace-branded card takes over: Sign in to your workspace (email + password, inline error states), an OIDC SSO button shown only when a provider is configured — new OIDC users are JIT-provisioned with the tenant's configured default role — a Not your workspace? escape hatch, plus a Create your organization entry. The discreet platform-admin sign-in was removed; a break-glass super-admin entry exists only at the root workspace card. Multi-org users pick their organization — one session = one tenant. Suspended-tenant blocking and tenant-bound credential errors still apply.

Tenant Root

5 · Tenant-Scoped Workspace, Root & Quotas

Tenant context in the header, a Root badge, locked root actions in the member list, alias editing (address fixed, header updates instantly), and a License & usage panel — with a blocked invite when the user quota is full.

Security Auditor

6 · Isolation Cues

Cross-tenant access attempts render as "Not found or no access" — deliberately generic, with no tenant-B data leaked — and are recorded as security events visible to the platform admin.

Enable multi-tenancy?

⚠️This action adopts your existing organization as a tenant — and tenant adoption is irreversible. You cannot return this deployment to its original pre-tenancy configuration.
  • Your current organization Parthenon Demo Org becomes the deployment's first tenant; its configuration and data remain intact — no reconfiguration of its identity provider is needed.
  • Tenant features become available: tenant registry, self-serve organization creation, per-tenant sign-in.
  • Disabling the switch later hides tenant features and restores single-tenant behavior without data loss — but the adoption itself cannot be undone.

Disable multi-tenancy?

ℹ️Tenant features will be hidden and the deployment returns to single-tenant behavior. No tenant data is lost — re-enabling restores everything.

Existing tenants, including the adopted organization, are retained in the registry.
