# Tech Spec: separate-optimization-from-execution

## Technical Overview

Before this change "Optimize & Verify" was entangled with execution: `POST /agents/sessions` accepted an `optimize: true` flag (`AgentJobCreate.optimize`) that converted the user's real run into an `optimize-and-verify` command side-execution — injecting `__command: optimize-and-verify` plus the command mission into `input_data` (`backend/app/api/v1/agents.py`), which replaced the agent's own system instruction at runtime (`runtime_executor.py` drops `system_instruction`/bindings/MCP context/plan for command runs). This epic splits the two concerns: a normal **Run** keeps the agent's own instructions and never optimizes, while a distinct, preconditioned **Optimize** action triggers a dedicated command execution that authors a `ready` optimized plan (or stops at `needs_feedback`). A later execution that falls back to the LLM path because of an optimized-artifact script marks the source plan `requires_fix` (new enum value) and appends an `execution_derived` feedback entry, surfacing a human-in-the-loop alert and a re-optimize path that carries the prior plan plus feedback.

**Refinement (authoring model + explicit-only + conversational exclusion).** Plan authoring is now decoupled from the agent's runtime model and from agent saves:

1. **One authoring model per workspace.** Implementation-plan generation and optimization-plan generation both resolve the tenant-level `TenantSetting.workflow_generation_model_id` (the setting already used for Skill/SOP workflow generation) for the session tenant (root tenant when multi-tenancy is off). `PlanGenerationService._invoke_llm` no longer uses `AgentType.model_id` and **no longer falls back to `select(ModelConfig).limit(1)`** — an unset value, or a value no longer present in the tenant's enabled model list, produces a structured "not configured / re-select" error and writes nothing.
2. **The optimization run itself executes on the authoring model.** `GET /internal/data/agent-types/{id}/context?session_id=…` already inspects the stored `AgentJob.input_data["__command"]` to gate the workflow-optimization inherent skill; it now additionally returns the **authoring** `model_id` + resolved `model_config_id` for command runs. Normal runs keep `AgentType.model_id`.
3. **Explicit generation only.** The `background_tasks.add_task(_run_plan_generation_bg, …)` scheduling on agent create (~1567) and update (~1778) is removed; generation happens only via `POST /agents/types/{type_id}/regenerate-plan`.
4. **Both plan generation and optimization are gated** on *authoring model configured & enabled* **and** *non-conversational agent*. Conversational agents (`AgentType.input_type == AgentInputType.conversation`) get a clear "not available" response and no generation anywhere.
5. **System Config** explains the three uses, recommends a larger model (advisory), reminds when unset, and the selection + options stay tenant-scoped.

All top-priority rules hold: three segregated backend services; agents and their scripts execute only in Agent Runtime (the sandbox runs AR-only); only Control Center touches PostgreSQL (all reads/writes below are CC-side; the resolver is a CC-only dependency and is never imported by AR/CH); agents never receive sensitive data (identity tokens resolved by CC, injected per tool call by CH — the context response carries model **identifiers** only).

**Refinement 2 (replay-only verification).** Optimization verification no longer touches live data. `execute_script` — the optimizer's verification primitive — validates a script **only** by replaying the exact reference input and the recorded tool responses of the selected execution:

1. **Capture.** The execution log now stores replayable evidence: `tool_call` carries structured `arguments` (from LangChain `inputs`) and an `input` text capped at 10,000 chars; `tool_response` carries the pairing `run_id`, `output` up to 50,000 chars and `output_truncated`. A sandboxed script's `script_tool_call` event carries the full recorded `result` (JSON, 50,000-char cap) next to `result_preview`.
2. **Transcript (CC-DB derived, no migration).** `_build_reference_transcript(db, agent_type_id, session_id=None)` selects the reference execution (latest completed NORMAL run, or an explicit one; command/current runs excluded) and returns `{session_id, input, input_schema, tool_calls: [{tool, arguments, response}], truncated}`. `script_tool_call` events are preferred; otherwise LLM `tool_call`/`tool_response` entries are paired by `run_id` in call order. `get_execution_log` returns the same `tool_calls`.
3. **Replay-only execution.** `execute_script` resolves the reference (optional `reference_session_id`, else the latest successful normal execution); with no recorded tool data it returns a structured `validation_error` and does **not** execute. Otherwise it forwards `reference_tool_responses` + `replay_required=True` (never the live path). AR answers every `tools.call` from `ReplayToolClient` (exact tool+arguments match, then next unconsumed entry for that tool) and fails with a typed sandbox error — "no recorded response for tool X" — on a miss. It never falls back to the live session-bound client.
4. **Mission.** `optimize-and-verify` instructs verifying by replaying the recorded reference `input`/`tool_calls`, using a tool call the reference never made ⇒ stop with `needs_feedback`.

Consequence: a script can no longer "pass" verification against live data and then fail at serving time on a different payload shape (the flight-search `str(dict)` class of bug), and an optimization run can never mutate data.

## API Changes

All public endpoints are JWT-authenticated (default), tenant-scoped, and enforce the existing `agent::*` permissions. Internal endpoints (AR→CC) use mTLS + signed tenant headers and are unchanged in transport.

### Public REST (Control Center)

- `POST /agents/sessions` (changed) — `AgentJobCreate` drops the `optimize` field; a normal launch always uses the agent's own system/skill instructions. No `__command` injection. Response: `202 AgentJobStatusRead` (unchanged).

- `POST /agents/sessions/optimize` (gate changed) — dedicated optimization trigger.
  - Request: `{ "agent_type_id": "<uuid>" }` (`AgentOptimizeRequest` — no user task input accepted or used).
  - Behavior: `404` when the agent type does not exist; then a **compound precondition check**, in this order, each returning `412 Precondition Failed` with a nested body `{ "detail": { "error": "optimize_gate_unmet", "reason_code": "<code>", "reason": "<human readable>" } }`:
    1. `reason_code: "conversational_agent"` — `input_type == conversation`; optimization is not available at all.
    2. `reason_code: "authoring_model_not_configured"` | `"authoring_model_not_enabled"` — no tenant authoring model, or the stored model is no longer in the tenant catalogue. No fallback model is used.
    3. `reason_code: "no_successful_execution"` — zero completed `AgentJob` rows for the agent type.
    Only when all three pass: run the shared `_resolve_launch_preflight` (user provenance, monthly quota, recursion pre-flight — the same helper a normal Run uses), count the execution at acceptance, inject `__command: optimize-and-verify` + `__command_agent_type_id` + the mission from `build_command_mission` (plus an "optimization-only run — no user task" directive), and dispatch CC → CH → AR as a command execution.
  - Response: `202 AgentJobStatusRead` (the optimization session).

- `GET /agents/types/{type_id}/optimization-gate` (extended) — plan/optimize preconditions (all computed, read-only), protected by `agent::read`; `404` when the agent type does not exist.
  - Response: `OptimizationGateRead` =
    ```json
    {
      "can_optimize": false,
      "can_generate_plan": true,
      "successful_executions": 0,
      "workflow_model_configured": true,
      "workflow_model_id": "gpt-4.1",
      "is_conversational": false,
      "reason": "Optimization requires at least one successful execution of this agent…",
      "reason_code": "no_successful_execution"
    }
    ```
  - Semantics:
    - `workflow_model_configured` is `true` only when the tenant setting is set **and** the model resolves in the current tenant's `enabled_models` (the derived "not configured / re-select" condition).
    - `workflow_model_id` echoes the stored value so the UI can say "`<id>` is no longer available — re-select" (it may be non-null while `workflow_model_configured` is `false`).
    - `is_conversational` = `AgentType.input_type == conversation`.
    - `can_generate_plan` = `workflow_model_configured && !is_conversational` (the successful-execution precondition does **not** apply to base-plan generation).
    - `can_optimize` = `can_generate_plan && successful_executions > 0`.
    - `reason` / `reason_code` describe the **first** unmet precondition (conversational → authoring model → executions); both `null` when `can_optimize` is `true`.
  - Backward compatibility: `can_optimize`, `successful_executions`, and `reason` keep their meaning/type; `reason_code` is additive.

- `POST /agents/types/{type_id}/regenerate-plan` (changed) — the **only** implementation-plan generation path.
  - `404` when the agent type does not exist.
  - Preconditions are checked **before** `ScriptRegistryService.retire_serving_versions` (never retire compiled scripts for a generation that cannot run), returning `412` with `{ "detail": { "error": "plan_generation_unavailable", "reason_code": "conversational_agent" | "authoring_model_not_configured" | "authoring_model_not_enabled", "reason": "<human readable>" } }` and writing no plan.
  - Otherwise: retire serving versions, author with the tenant authoring model, return `AgentTypeRead` (unchanged shape) with the refreshed `plan`.
  - A failed attempt (model error/timeout) records `generation_status: "failed"` + `generation_error` **without discarding** the last successful `plan_steps`/`topology`/`agent_config_hash`/`generated_at`.

- `GET /agents/model-configs/workflow-generation` (unchanged behaviour, tenant-scoped) — `selected_model_id` (raw stored value, so a now-disabled selection is still visible) + `options` built **only** from the session tenant's model configs. UI consumes this for the authoring-model selector.

- `PUT /agents/model-configs/workflow-generation` (unchanged behaviour, tenant-scoped) — persists the session tenant's selection; `422` when the model id is not enabled in the tenant's catalogue (`null` clears the selection). The larger-model recommendation is **advisory only** — any enabled model is accepted.

- `GET /agents/types/{type_id}/optimized-plan` (unchanged shape, new values) — `_optimized_plan_payload` already serialized `status` and `feedback_comments` verbatim, so `status` may now be `requires_fix` and `feedback_comments` entries carry `source` (`manual` | `execution_derived`) plus optional `source_execution_id` / `source_fallback_event_id` with no serializer change. Entries also carry `created_at`, `raw_feedback`, and `summary`.

- `POST /agents/types/{type_id}/optimize-plan/feedback` (changed behavior) — manual feedback is now appended with `"source": "manual"` (readers treat a missing `source` as `manual`).

### Internal REST (AR → CC, mTLS)

- `GET /api/v1/internal/data/agent-types/{agent_type_id}/context?session_id=…` (changed) — the handler already resolves the `AgentJob` to gate the workflow-optimization inherent skill; it now branches the model too:
  - session `input_data["__command"]` set (command run, currently `optimize-and-verify`): `model_id` / `model_config_id` return the **tenant authoring model** and its resolved config id.
  - no `__command` (normal run, conversational prepare, auto-compile, turn resume): `model_id` / `model_config_id` keep returning `AgentType.model_id` and the config that enables it.
  - Authoring-model resolution failure on a command run → `412` with `{ "detail": { "error": "authoring_model_unavailable", "reason_code": …, "reason": … } }`; the run fails closed (AR surfaces the error) rather than silently executing on the agent model. Only identifiers are returned — never credentials or tokens (AR fetches the config via `GET /model-configs/{id}`).

- `POST /api/v1/internal/scripts/fallbacks` (changed behavior) — after recording the `FallbackEvent`, `ScriptRegistryService.record_fallback` resolves `script_version_id → ScriptDefinition.source_optimized_plan_id → OptimizedImplementationPlan`; when a live (non-retired) plan is attributed, it is set `requires_fix` and an `execution_derived` feedback entry is appended in the same transaction. No request fields change (`FallbackReportRequest` is untouched) — attribution is entirely CC-side.

- `GET /api/v1/internal/scripts/optimized-plan` (unchanged behavior) — returns only the fresh `ready` plan (`get_fresh_optimized_plan` filters `status == ready`), so a `requires_fix` plan is naturally never served.

- `POST /api/v1/internal/system-tools/get-execution-log` (changed) — lists recent NORMAL executions (newest first; `executions_limit` default 10, max 50), excluding command (optimization) runs and the current session; selects the latest completed normal execution (or an explicit `session_id`); returns that execution's `entries` and `text` log chronologically, bounded by `limit` (default 100, max 500), plus its reference `input`, the agent's `input_schema`, and the replay transcript `tool_calls` (`{tool, arguments, response}`) with `transcript_truncated`. The transcript window is the full 500-entry replay window (the returned text log stays bounded by `limit`).

- `POST /api/v1/internal/system-tools/execute-script` (changed — REPLAY ONLY) — resolves the reference execution (optional `reference_session_id`, else the latest successful normal execution) and replays it. With no recorded `tool_calls`: `{ "status": "validation_error", "error": "No reference tool data is available ..." }` and nothing executes. Otherwise CC forwards `python_source` + the reference `input` + `reference_tool_responses` + `replay_required=True` through `forward_sandboxed_script` (CC→CH→AR) and returns `{output, replayed, reference_session_id, transcript_truncated}` (or `{error}` from AR). Live MCP tools are never invoked and no data is mutated.

- `POST /internal/script-tools/forward` (CH, changed) — `ScriptForwardRequest` accepts `reference_tool_responses` + `replay_required` and passes both to AR's `/internal/script-tools/execute`.

- `POST /internal/script-tools/execute` (AR, changed) — `ScriptToolExecuteRequest` accepts `reference_tool_responses` + `replay_required`. With `replay_required`, the sandbox runs with `ReplayToolClient` (recorded responses only; a tool call with no recorded response fails the run with a typed "no recorded response for tool X" error) and a missing transcript is a structured error — never a live fallback. Without it (agent-invoked `script____<name>`), the session-bound live client is unchanged.

- `POST /api/v1/internal/system-tools/generate-optimized-plan` (changed) — now enforces an explicit authoring allow-list: `status` must be `ready`, `failed`, or `needs_feedback`; any other value (notably `requires_fix`, which is set only by the fallback path) is rejected with a structured `{ "status": "validation_error", "error": "..." }` result and no plan is written. `needs_feedback` continues to persist `error`.

### Error contract (reason codes)

| `reason_code` | Produced by | Meaning / UI |
|---|---|---|
| `conversational_agent` | `regenerate-plan`, `sessions/optimize`, gate | Plan generation and optimization do not exist for conversational agents; controls hidden/disabled with an explanation |
| `authoring_model_not_configured` | same | No authoring model set for this workspace → "configure it in System Config"; nothing generated, no fallback |
| `authoring_model_not_enabled` | same | Saved authoring model is no longer in the workspace catalogue → "re-select a model in System Config" |
| `no_successful_execution` | `sessions/optimize`, gate | Run the agent successfully at least once first |
| `authoring_model_unavailable` | internal context (command runs only) | Race: config removed between trigger and execution; run fails closed |

`extractOptimizeGateReason` in `frontend/src/utils/errorUtils.ts` is generalized to read `reason_code` + `reason` from the nested `412` detail (and keeps working when only `reason` is present); a sibling `extractPlanGenerationReason` handles the identical shape for `plan_generation_unavailable`.

## Data Access Patterns

Control Center is the sole database gateway; Agent Runtime consumes everything via CC internal REST (mTLS). No new entity, column, or FK for the refinement either — one enum value plus a backward-compatible JSON shape extension, and a behavioural trigger/resolution change.

- **Authoring-model resolution (read, tenant-scoped)** — `require_authoring_model` / `get_authoring_model_state` read `TenantSetting(tenant_id, "workflow_generation_model_id")` for the session tenant (`_session_tenant_id`: request context, else root tenant) and resolve the model id against `ModelConfig.enabled_models` via the session-scoped `db` (the same auto-tenant-filtered query path used by `ModelBindingLayer.resolve_model_config` and `ModelConfigService.list_model_configs` — no hand-written tenant filter, no raw client). "Not configured" (blank/absent) and "not enabled" (id absent from every enabled-model list) are **derived at read time**; the setting row is never rewritten. No fallback branch exists: an unusable state raises/returns instead of selecting another model.

- **Plan authoring (write, explicit only)** — `POST /agents/types/{type_id}/regenerate-plan` → `PlanGenerationService.generate_plan` → `AgentPlan` upsert. The service performs one authoring read (above) and one model call through `ModelBindingLayer.complete_from_context(model_id=<authoring>, model_config_dict=…, …)` (the ORM-based `complete()` cannot be used — it derives `model_name` from `AgentType.model_id`). Not-configured → **no write at all**; model failure → `generation_status="failed"` + `generation_error` while retaining the last successful steps/topology/hash/`generated_at`. Nothing schedules this path implicitly: create/update no longer enqueue a background task.

- **Command-run model override (read)** — the internal context handler reads `AgentJob.input_data["__command"]` (single row by `session_id`, already loaded for inherent-skill gating), then resolves the authoring model once and returns `model_id` + `model_config_id`. Only identifiers cross the boundary; AR fetches credentials via `GET /internal/data/model-configs/{model_config_id}`.

- **Gate (read-only, computed)** — three cheap reads composed in `AgentSessionService.get_optimization_gate`: tenant authoring-model state, `AgentType.input_type`, and `COUNT(*) AgentJob.status == completed`. No counter, no stored flag. The endpoint and the optimize trigger both use the same helper, so UI and server agree; the trigger re-checks server-side.

- **Serving / execution preference (read)** — `ScriptRegistryService.get_fresh_optimized_plan` reads only `status == ready` plans (fresher than the base plan); `get_serving_version` reads compiled script versions. The dispatcher (`dispatch.py`) fetches these via `ScriptRegistryClient` (`GET /serving-version`, `GET /optimized-plan`); no caching (freshness note).

- **Fallback → requires-fix (write)** — `FallbackController` reports `fell_back` (`POST /executions`) then `POST /fallbacks`; `ScriptRegistryService.record_fallback` writes the `FallbackEvent`, degrades script health, then `_flag_optimized_plan_for_fallback` resolves attribution through `ScriptDefinition.source_optimized_plan_id` and — when attributed to a live plan — invokes `OptimizedPlanService.mark_requires_fix` (writes plan `status` + appends `feedback_comments`, targeting the attributed `plan_id`). All writes are CC-only, in one transaction.

- **Feedback (append-only JSON)** — `feedback_comments` stays a JSON list; manual entries (`add_feedback`, UI) carry `source: "manual"`; execution-derived entries carry `source: "execution_derived"` + `source_execution_id` (soft UUID to `ScriptExecutionRecord`) + optional `source_fallback_event_id`. Both are included verbatim in the authoring prompt on regeneration.

- **Re-optimization** — re-triggering optimize after `requires_fix`/`needs_feedback` generates a new plan (the old one is marked `retired` by `_upsert_optimized_plan`), carrying the prior plan + full `feedback_comments` memory as context.

- **System Config (read/write, tenant-scoped)** — `GET` lists options from the session tenant's model configs and returns the raw stored selection; `PUT` validates the model id against that same tenant catalogue and writes the tenant's own `TenantSetting` row. There is no global/root fallback write and no second setting.
