## Sandbox Technology Decision — COMMITTED: RestrictedPython

**Decision: adopt [RestrictedPython](https://github.com/zopefoundation/RestrictedPython) (Zope Foundation, actively maintained, Python 3.11-compatible).** Added as a pinned dependency in `backend/pyproject.toml` (`RestrictedPython~=7.x`).

Evaluation against WASM alternatives (Pyodide / QuickJS-in-WASM):

| Criterion | RestrictedPython (in-process) | WASM sandbox (Pyodide/QuickJS) |
|---|---|---|
| Runtime footprint | None — runs inside Agent Runtime | Separate WASM runtime, second supply chain |
| MCP tool call path | Direct call into injected `CommHubToolClient` | Serialization boundary on every call (JSON across WASM) |
| Model-backed steps in scripts | Direct semantic-bridge call | Same serialization penalty |
| Observability | Native OTEL/logging integration | Degraded; correlation across boundary |
| Isolation strength | AST-level (guarded builtins, no import statement, `_getattr_`/`_write_` guards) + OS resource limits | Stronger memory isolation |
| Threat-model fit | No untrusted-user scripting (out of scope per PRD); scripts are model-authored and validated; MCP-only egress | Over-engineered for this threat model |

Rationale: the required invariants (no I/O, allowlist-only imports, resource caps, fail-closed escapes) map 1:1 to RestrictedPython's hardened compile/exec model (`compile_restricted`, `safe_globals`, custom `_getattr_`/`_getitem_`/`_write_`/`_import_` handlers). Memory/CPU/wall-time caps are enforced with OS-level `resource` limits + asyncio timeouts around execution, which WASM's stronger memory isolation would not improve given the process is already isolated per-service. **Defense in depth**: RestrictedPython is one layer; the validator (AST checks, secret-shape guard), OS resource caps, and the single injected MCP-only client are independent enforcement layers.

## Data Access Patterns

- **Ownership invariant:** all schema changes are Control-Center-owned (sole DB gateway). AR reads/writes registry, execution records, and mock recordings exclusively through CC REST (`internal_httpx_client`, signed tenant headers, mTLS) — `backend/app/agent_runtime/scripts/cc_client.py` pattern extended with mock-recording methods.
- **ScriptVersion:** reads by agent-type serving lookup (unchanged); writes only through lifecycle transitions; `python_source` + caps are immutable per version.
- **ScriptExecutionRecord:** append-only per execution; new accounting fields written at execution completion via the existing CC execution API.
- **LLMMockRecording:** written in record mode (batched at run end), read in replay mode by `recording_key` within tenant; index lookups on `(tenant_id, recording_key)`; no relationship to ScriptVersion (keyed by request content, per data-model.md).
- **Fallback events:** append-only; new enum reasons; no query-pattern changes.
- **Alembic:** one migration chain under `backend/alembic/versions/` — new enums via model import + `postgresql.ENUM(..., create_type=False)`; `ALTER TYPE ... ADD VALUE` via string-formatted DDL; new table + columns per data-model.md §5; downgrade drops new objects only.
