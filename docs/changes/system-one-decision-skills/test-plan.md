# Test Plan: System One Decision Tools

## 1. Test Strategy

- **Unit tests (backend)** — Pure-logic validation: per-question-type rules (Choice/Score/Noul), auto-generated tool description composition, per-tenant name uniqueness rules, state preset mapping, confidence gate computation, provider resolution. Fast, no DB.
- **Backend integration tests** — Real PostgreSQL via test fixtures; migration application (`alembic upgrade head`) in setup; decision tool CRUD + per-tenant name uniqueness via API; auto-generated description correctness; execution engine keyed to tools with mocked TypeSafe transport (injected client) plus persisted `DecisionExecutionResult`; tenant isolation of tools and results; MCP registry bridge behavior; encrypted key storage verified at the DB level.
- **Frontend unit/component tests (Vitest)** — Provider config form (write-only key, dialog error handling), Decision Tools page/form (configured-model gate, question builder per type, schemas, state preset, generated-description preview, thresholds), decision results view rendering; skills editor regression (original editor, no decision-specific UI).
- **E2E tests (Playwright)** — Mocked variants for tool authoring/execution flows; **one real-backend variant** (no mocks) exercising the actual API, DB, migration, tenant isolation, MCP exposure, and permission enforcement.
- **Manual testing** — Against live TypeSafe Jev API (`jev-latest`): real key round-trip, actual structured answers, confidence values plausibility. Verify MCP `tools/list` shows `decision:`-prefixed tools per tenant. Verify i18n coverage of all new UI strings. Verify skill authoring/executing behaves exactly as before the change (revert regression).

## 2. Coverage Areas

- **Provider config CRUD + encrypted key storage** — Critical: credentials must never leak. Verify create/read/update/delete via API, key encrypted at rest (ciphertext in DB column, not plaintext), key never returned by any response (list/detail), decryption only at call time via `CredentialVault`, and `system::system_one` permission enforcement on every provider route.
- **Decision tool CRUD + per-tenant name uniqueness** — Critical: tool names are unique within a tenant only. The same tool name (e.g. `decision:tool_a`) must be creatable independently in two tenants with both rows persisting; a duplicate name within one tenant must be rejected with a structured validation error. All tool lookups, mutations, and results are tenant-filtered.
- **Auto-generated tool description correctness** — Critical: skills, agents, and MCP clients select tools based on it. Verify the description is generated from the definition (purpose, questions, input/output schemas), stored on the entity, returned by CRUD Read responses and the description endpoint, and regenerated on update. Verify the generated description is what appears in the MCP catalog.
- **Authoring validation per question type** — Critical: malformed questions would produce invalid model evaluations. Choice requires non-empty options; Score requires an ordered legend; Noul carries no criteria; at least one question required; state preset mapping validated; structured input/output schemas required and validated.
- **Authoring gate (configured-model check)** — Critical UX and data integrity: creating/updating a decision tool with no enabled System One model must be blocked with a clear structured error; allowed when a provider is configured.
- **Execution path (keyed to tools)** — Critical: correctness of the whole orchestration — tool resolution within the caller's tenant, state preset application to input/agent data, single dispatch of all questions via the system-tools execution path (`decision:`-prefixed dispatch), response normalization into typed answers (values, probabilities, confidence, legend), and result persistence keyed to `decision_tool_id`.
- **Confidence gating** — Critical: automated action depends on it. confidence ≥ act → `act`; ≥ confirm → `confirm`; else `escalate`; boundaries tested at exact threshold values.
- **MCP exposure with `decision:` prefix** — Critical: external MCP clients consume decision tools through the Communication Hub bridge. Verify `tools/list` includes `decision:`-prefixed tools with the auto-generated description and structured input schema alongside system tools; `tools/call` for `decision:` names is forwarded to Control Center's system-tools execution path; the tenant-scoped catalog only exposes the caller's tenant's tools.
- **Permission / resource-type enforcement** — Critical: decision tools are granted like system tools through the existing role → tool permission path (no parallel permission system); `system::system_one` must be registered in both backend and frontend manifests or ALL users (including wildcard admins) get 403. Unauthenticated access must fail on all new routes.
- **Skills regression (revert)** — Critical: skills are unchanged/reverted. Verify no `decision` skill type exists (no `skill_type` column), skill editor renders the original form, skill CRUD/execution flows behave identically to before the change, and the skill executor has no decision delegation.
- **Migration** — Critical: schema must exist or everything fails at runtime. Verify decision tool tables with unique `(tenant_id, name)` constraint, `decision_skill` tables and the `skill_type` discriminator dropped, results re-keyed to `decision_tool_id`, `system_one_provider_configs` present, constraints enforced, and downgrade is reversible.
- **Routing boundaries (top-priority rules)** — Communication Hub forwards `decision:` invocations without credentials; Agent Runtime receives structured results only; no agent-visible payload contains key material.
- **Provider base URL preset (round 2)** — The System One provider base URL is preset to `https://api.typesafe.ai/v1` and is not editable: API create/update must accept no base-URL override (or ignore/reject it), the config response always reports the preset URL, and the UI renders it read-only.
- **Provider test-connection endpoint (round 2)** — Critical: the "Test connection" button validates key + endpoint before the config is relied upon. Verify the endpoint performs a real validation call against the provider, returns a status-only result (success, or a clear failure reason) and never echoes the API key or any derived key material in the response, logs, or error details; verify unauthenticated/permission-denied behavior and timeout handling.
- **Reserved `decision` naming in tool registry & MCP hub (round 2)** — Critical: "decision" is a reserved namespace word (like "system") in `RESERVED_SERVER_NAMES`. Verify the backend constant includes `decision`, that creating/editing a decision tool whose computed name would collide with the namespace is handled, and that the MCP hub rejects any new server slug named `decision` with HTTP 409 (mirroring `system` slug rejection).
- **Decision tools in the skill-authoring tool registry (round 2)** — Saved decision tools must be listed in the tool registry when defining skills exactly like system tools: same registry endpoint/source, carrying the auto-generated description and structured input schema, distinguishable as decision tools, and selectable/grantable in the skill authoring flow.
- **AgentDataType input/output references (round 2)** — Critical: decision tool input/output are existing Agent Data Types, not hand-written schemas. Verify CRUD accepts and persists AgentDataType IDs (validating existence within the tenant), that deleting an AgentDataType referenced by any decision tool is blocked with a clear error, and that the auto-generated tool description is derived from the referenced types' field definitions (regenerated when the definition changes).
- **AI generate endpoint (round 2)** — The generation endpoint (same mechanism as agent-skill instruction generation) receives description + chosen input/output data types and drafts questions and state mapping. Verify it returns draft questions/mapping valid against the per-type authoring rules, never includes API key material anywhere in request handling or response, and fails gracefully (structured error, no partial tool persisted) when the model call fails or returns malformed output.
- **State placeholder auto-detection (round 2)** — The form auto-detects backtick-quoted object/state path placeholders (e.g. `` `input.tier` ``) in Jev question instructions and surfaces them for mapping. Verify extraction of dot/bracket paths, dedupe, handling of unknown/invalid paths, and that detected placeholders correspond to mappable properties of the chosen input data type.
- **Frontend decision tool form flow (round 2)** — Field order is fixed (name, description, input/output data types as first definable rows, then questions, then state mapping); input/output data type View dialogs render the referenced AgentDataType read-only inside the form; after selecting the input data type, mapping property selectors populate automatically from its properties. Verify all three via component tests.

## 3. Critical Scenarios

- WHEN a platform admin creates a provider config with an API key, THEN the stored DB value is ciphertext, and no list/detail/status response contains the key or any reversible form.
- WHEN a provider config is updated with a new key, THEN the old ciphertext is replaced and the previous key no longer decrypts to anything used at call time.
- WHEN a provider config is deleted, THEN `GET /system-one/status` reports unconfigured and decision-tool authoring becomes blocked.
- WHEN a tool author starts creating a decision tool with no enabled System One model, THEN the authoring flow is blocked with a clear message and no decision tool can be persisted.
- WHEN a tool author creates a decision tool with a configured model, THEN the form proceeds and the definition form is driven by the configured model's API definition.
- WHEN a decision tool is created with zero questions, THEN creation is rejected with a validation error.
- WHEN a Choice question is saved with an empty options list, THEN validation fails; WHEN a Score question lacks an ordered legend, THEN validation fails; WHEN a Noul question has criteria attached, THEN validation fails.
- WHEN a decision tool is created with an invalid state preset mapping or missing input/output schemas, THEN creation is rejected.
- WHEN a decision tool is created, THEN the response includes an auto-generated description derived from the definition; WHEN the tool is updated, THEN the stored description is regenerated and reflected in Read responses and the description endpoint.
- WHEN tenant A defines a decision tool named "tool_a" and tenant B defines an identically named "tool_a", THEN both persist as separate tenant-scoped rows; WHEN each tenant invokes its tool, THEN each invocation resolves within its own tenant with no cross-tenant visibility.
- WHEN a duplicate tool name is created within the same tenant, THEN creation is rejected with a structured uniqueness error and no partial rows (questions) persist.
- WHEN a decision tool is executed with valid input, THEN one evaluation dispatch carries the constructed state plus ALL predefined questions, and the response contains a structured typed answer per question with probabilities and confidence.
- WHEN execution completes, THEN a `DecisionExecutionResult` row keyed to the decision tool is persisted with state snapshot, per-question answers, gate outcome, status, and provider model, and is queryable via the decision results endpoint.
- WHEN tenant A executes its "tool_a" and tenant B queries results, THEN tenant B sees none of tenant A's results (results are tenant-filtered by the tool's tenant).
- WHEN confidence equals the act threshold exactly, THEN the outcome is `act`; WHEN confidence is between confirm and act, THEN `confirm`; WHEN below confirm, THEN `escalate`.
- WHEN an MCP client in tenant B calls `tools/list`, THEN only tenant B's `decision:`-prefixed tools appear (plus system tools), each carrying the auto-generated description and structured input schema; tenant A's tools are absent.
- WHEN an MCP client calls `tools/call` with a `decision:`-prefixed name, THEN Communication Hub forwards it to Control Center's system-tools execution path without credentials and returns the structured result.
- WHEN a skill (or agent/SOP) references a decision tool, THEN it invokes it through the existing system-tool invocation path and normal tool permission grants apply.
- WHEN an agent without a role grant to the decision tool invokes it, THEN the invocation is denied through the normal tool permission path.
- WHEN any user calls provider config routes without `system::system_one` permission, THEN access is denied; WHEN a wildcard-permission admin calls them, THEN access is allowed (manifest registered correctly).
- WHEN Communication Hub receives a `decision:` tool invocation, THEN it forwards to Control Center and its logs/payloads contain no API key material.
- WHEN the TypeSafe API returns a malformed or partial answer set, THEN execution fails gracefully with a logged error and no partially persisted result presented as successful.
- WHEN existing skills are listed, authored, and executed after the revert, THEN behavior is identical to the pre-change baseline: no `decision` skill type is offered or accepted, the `skill_type` column is gone, and the editor shows the original form.
- WHEN a provider config is read, THEN the base URL is the preset `https://api.typesafe.ai/v1` and cannot be changed via API or UI; WHEN an update attempt supplies a different base URL, THEN it is rejected (or ignored) and the preset remains.
- WHEN the provider test-connection endpoint is called with a valid configuration, THEN it returns a success status result and no response field contains the API key or any key-derived material; WHEN called with an invalid key or unreachable endpoint, THEN it returns a clear failure status (with reason) and likewise no key material; WHEN called without `system::system_one` permission, THEN access is denied.
- WHEN a user attempts to create an MCP server with slug "decision", THEN the MCP hub rejects it with HTTP 409 (slug reserved, mirroring "system"); WHEN `RESERVED_SERVER_NAMES` is inspected, THEN it contains "decision".
- WHEN the skill-authoring tool registry is queried, THEN saved decision tools are listed alongside system tools with their auto-generated description and input schema, and can be selected and granted exactly like system tools.
- WHEN a decision tool is created/updated with AgentDataType IDs for input and output, THEN they are persisted and validated to exist within the tenant; WHEN a referenced AgentDataType is deleted, THEN deletion is blocked with a clear error; WHEN the tool description is generated, THEN it is derived from the referenced types' field definitions.
- WHEN the AI generate endpoint is called with a description + chosen data types, THEN it returns drafted questions and state mapping that pass per-type authoring validation and contain no key material; WHEN the underlying model call fails or returns malformed output, THEN a structured error is returned and no partial tool state is persisted.
- WHEN a Jev question instruction contains backtick-quoted paths like `` `input.tier` ``, THEN the form auto-detects and lists them as mapping placeholders; WHEN a detected path does not exist on the chosen input data type, THEN it is surfaced as unmappable/invalid rather than silently mapped.
- WHEN the decision tool form renders, THEN fields appear in the fixed order (name, description, input data type, output data type, questions, state mapping); WHEN the author clicks View on an input/output data type, THEN a read-only dialog shows the AgentDataType definition without leaving the form; WHEN the input data type is selected, THEN the state-mapping property selectors populate automatically from its properties.

## 4. Edge Cases & Risks

- **Migration not applied** — Tests pass against mocked backends while production DB lacks new tables; mitigated by real-backend tests and alembic in test setup (see Pre-Test Checklist).
- **Migration data loss risk** — The migration drops `decision_skill` tables and `skill_type`; verify downgrade reversibility and that no skill rows are lost when the discriminator column is dropped.
- **Name uniqueness edge cases** — Case sensitivity/whitespace in tool names ("Tool_A" vs "tool_a"); uniqueness enforced at DB level (unique constraint) as well as service level; rename (PUT) colliding with an existing name in the same tenant must be rejected.
- **Cross-tenant leakage** — Tool IDs guessed/enumerated across tenants must 404 (tenant-filtered), not leak definitions, descriptions, or results.
- **Legacy skills after migration** — Existing skills must keep executing unchanged; verify the executor's original path is fully restored and no code references the removed `skill_type`.
- **Key update edge cases** — Empty key on update (must keep existing), whitespace key, update of non-key fields only must not touch stored ciphertext.
- **Threshold misconfiguration** — act threshold lower than confirm threshold; define and test validation or documented behavior.
- **Multiple provider rows** — Only one enabled provider should resolve for execution; behavior when several exist or when the enabled provider is deleted mid-flight.
- **Provider unavailable / network failure** — No LLM fallback (per out-of-scope); execution must fail with clear status, and results must not be persisted as successful.
- **State preset edge cases** — Missing input keys referenced by the mapping; agent data absent at execution time; empty state.
- **Question ordering** — Answers must map back to questions positionally/stably regardless of provider response ordering.
- **Confidence semantics** — Provider returning confidence outside expected range or missing per-question confidence.
- **Description generation edge cases** — Very long questions/schemas, empty purpose, special characters — generated description must remain valid for MCP consumers.
- **MCP catalog sync** — Tool created/deactivated/deleted must appear/disappear from `tools/list` promptly; stale catalog entries after tenant deletion.
- **Multi-tenancy** — Provider configs, tools, and results scoped to the correct tenant; cross-tenant reads denied; tenant containment applies to all managed data records.
- **i18n** — All new UI strings via `t()`; missing translation keys fail tests.
- **Risk: encrypted-key regression** — Any logging/serialization change could leak plaintext; integration tests assert ciphertext at rest and absence in responses/logs.
