# Database Migrations — Reference Log

Canonical record of all Alembic migration revisions applied to the Parthenon database. Update this document whenever a migration is promoted to production.

Migration scripts live in `backend/alembic/versions/`. Apply them with `alembic upgrade head` from the `backend/` directory. Verify the active revision with `alembic current` or by querying the `alembic_version` table.

## Notes

- Migrations `001_baseline` through `d736a85c26fd` are **purely additive** — no existing table or column was dropped or renamed.
- Migration `df2225d787c5` is the first **destructive migration**: it removes columns from `agent_type` (`sop_id`, `identity_subject`, `system_prompt`, `mode`) and drops the `agent_skill_assignment` table. Complete the AgentType data backfill (Step 2 of the change deployment doc) before applying to production. Reverting this migration via `alembic downgrade -1` will drop all new tables and data.
- The `d736a85c26fd` migration must be verified to contain no `op.drop_table` or `op.drop_column` calls before applying to production. See `docs/changes/user-permission-management/deployment.md` Step 1 for the full verification checklist.
- Migration `5c2910c238a8` adds a PostgreSQL enum value (`passthrough`) using `ALTER TYPE … ADD VALUE`. PostgreSQL does not support removing enum values, so the `downgrade()` function for this migration is a **no-op** — rolling back Alembic to the prior revision (`fcbe5b250e08`) will not remove the `passthrough` value from the `mcp_session_auth_type_enum` type. This is safe: the previous code ignores unknown enum values at the application layer. See [rollback.md](rollback.md) Step 3 for the full implication.
- For new environment bootstraps, run `alembic upgrade head` once after the database is initialised (see [first-time-deployment.md](first-time-deployment.md) Step 3). The head revision is automatically determined from the migration chain.
- Migration `385c4ae051f6` is **additive with a safe data migration**: new tables are created, all new columns on `agent_identities` are nullable, and existing `refresh_token` values are copied to `encrypted_refresh_token` during upgrade. Old code that does not reference the new columns continues to work. Rolling back via `alembic downgrade -1` drops all new tables and removes the three `agent_identities` columns; the copied data in `encrypted_refresh_token` is lost. The Control Center will re-initialise the Certificate Authority on next startup if the tables are absent.
- Migration `b3c9d4e5f6a7` adds a PostgreSQL enum (`model_usage_unit_enum`) and a column with `server_default='k'`. Rolling back via `alembic downgrade -1` drops the `unit` column. Old code that does not reference the new column continues to work because the default is applied at the database level.
- Migration `c1a2b3d4e5f6` is the first **destructive guardrail migration**: it drops four `usage_limit_*` columns from `model_guardrail_configurations`, restructures the table to one row per `(model_id, model_name, period)`, adds `is_disabled` to `model_configs`, and creates `model_availability` with a backfill. Rolling back via `alembic downgrade -1` is destructive — any guardrail rows added under the new shape are lost. Complete the per-period guardrail data backfill before applying to production. The `model_guardrail_period_enum` and `model_availability_disabled_reason_enum` types cannot be dropped cleanly if other rows reference them.
- Migrations `d2e3f4a5b6c7`, `e3f4a5b6c7d8`, and `f4a5b6c7d8e9` each add a PostgreSQL enum value (`model_disabled`, `vendor_disabled`, `guardrail_breached`, `terminated`). PostgreSQL does not support removing enum values, so the `downgrade()` functions for these migrations are **no-ops** — rolling back Alembic to the prior revision will not remove the enum values. This is safe: the previous code ignores unknown enum values at the application layer.
- Migration `aad0f4a3b3bc` is **additive with column extensions**: it creates 8 new governance tables and adds new columns to `agent_jobs`, `agent_types`, and `execution_log_entries`. The new columns are nullable. Old code that does not reference the new columns continues to work. Rolling back via `alembic downgrade -1` drops all new tables and removes the new columns. The Control Center remains the only service that writes to these governance tables; Agent Runtime reads termination outcomes and policy events through the Communication Hub.
- Migration `b38732c813c9` is **additive with a destructive column removal**: it creates two new join tables (`agent_type_sop_bindings`, `agent_type_skill_bindings`) and removes the `primary_sop_id` column from `agent_types`. The data migration in the upgrade step copies existing `primary_sop_id` values into `agent_type_sop_bindings` rows with `order=0`. Rolling back via `alembic downgrade -1` drops the two join tables but does not restore the `primary_sop_id` column — the `downgrade` function recreates the column as nullable UUID. Existing Agent Types that relied on `primary_sop_id` will have a `NULL` value after rollback. Verify that no production code reads `primary_sop_id` before applying this migration to production.
- Migration `65b29c8fcdbc` is **additive** — no existing tables, columns, or constraints are modified or removed. The `downgrade()` drops both new tables (`agent_api_keys`, `api_key_usage_logs`) and the two new enum types (`agent_api_key_status_enum`, `api_key_usage_action_enum`). Any API keys created during the deployment window are permanently lost on downgrade. A separate one-time data backfill is required for `skills.updated_at` (sets `NULL` values to `created_at`) — this is a data operation, not a schema migration, and must be verified before enabling the `since` parameter on `load_skills`. Only Control Center connects to the database; Communication Hub and Agent Runtime consume API key validation results via the Control Center internal API and are unaffected by the schema changes.
- Migration `868d278f04db` is a **data-only migration** — no schema changes (no new tables, columns, or constraints). It transforms legacy flat resource type values in `policy_statements.module` and `policy_resources.resource_type` to the new `module::submodule` namespaced format. The migration is **idempotent** — rows already containing `::` are skipped. Downgrade provides **best-effort reversal**: 1:1 renames are reversed, `*::*` transforms back to `*`, and consolidations map to a single representative value (`agent::trails` → `conversation`; `system::permissions` → `permissions`). Any policy statements or resources created after the migration with new namespaced values will be left unchanged. After migration, the backend validates all resource types against the namespaced manifest and rejects flat values. The migration must complete before the updated backend starts serving traffic to avoid inconsistent permission evaluation. Only Control Center connects to the database; Agent Runtime and Communication Hub consume permission data via the Control Center API and are unaffected by the data migration.
- Migration `49ab45b8226e` is **destructive** — it renames columns (`oidc_provider_url` → `issuer_url`, `client_secret` → `encrypted_client_secret`), removes columns (`realm_name`, `audience`, `is_setup_complete`, `setup_completed_at`, `setup_completed_by_id`), and changes enum values (`provider_type` enum from `keycloak_bundled | keycloak_external | azure_entraid` to `oidc_generic | keycloak | azure_entraid`). **Prerequisite:** `config/identity.yaml` must be present and accessible from the Control Center container for the one-time data migration that follows. The data migration (YAML → DB) is handled by the Bootstrap Service at startup, not by Alembic. Rolling back via `alembic downgrade -1` drops `super_admin_credentials` and `identity_provider_config_audits` tables, reverts all schema changes on `identity_provider_configs` and `identity_provider_setup_state`, and restores the original enum values. Any DB-stored OIDC configs created via the UI or migration are lost on downgrade — `config/identity.yaml` is the restoration source. See [rollback.md](rollback.md) Change-Specific Rollback: Refine OIDC Integration for the full rollback procedure.
- Migrations `31c0e0bc9990` through `b8e4f2a6c9d1` form the **multi-tenancy chain** (apply in chain order via `alembic upgrade head`; `b8e4f2a6c9d1` is the head): `31c0e0bc9990` → `b4d7e1a90c2f` → `c8e2f5b17a93` → `d9f3a6c2e7b1` → `6363bb7ee8c3` → `a1f2c3d4e5b6` → `b8e4f2a6c9d1`. The chain is **additive and backward compatible** — it only adds new tables and nullable tenant reference columns with indexes; it drops nothing and makes nothing non-nullable. The migration does **not** enable tenancy: the `multi_tenancy_enabled` platform setting is seeded `false` and the adoption backfill runs only when the switch is deliberately enabled. Rolling back via `alembic downgrade` **drops the tenant tables and tenant reference columns** — export/backup all tenant data (tenants, memberships, invitations, tenant audit events, per-tenant OIDC configurations) before any downgrade. See [rollback.md](rollback.md) Change-Specific Rollback: Multi-Tenant Support.
- Migrations `b8c9d0e1f2a3` and `c9d0e1f2a3b4` form the **strict-tenant-isolation chain** (apply in order via `alembic upgrade head`; `c9d0e1f2a3b4` is the head, chained after `a7b9c1d3e5f7`). **Deploy order rationale: CC → AR → CH** — Control Center owns the database, migration tooling, tenant resolution, and the CA, so it must come up first against the tightened schema; Agent Runtime depends on CC for certificate bootstrap and tenant-context verification; Communication Hub needs both CC and the new AR header-forwarding behavior. Restart via `parthenon.ps1 restart -Services backend -Force`. **Pre-flight / post-migration verification:** before applying, record the count of NULL-tenant rows per affected table (rollback baseline); after applying, every such table must report zero NULL rows and `alembic current` must report head. **Rollback caveat:** `b8c9d0e1f2a3`'s downgrade restores the schema only (platform-wide slug unique, global partial indexes, nullable `tenant_id`) — rows adopted into the root tenant **keep their root-tenant binding** and cannot safely return to NULL once strict `(tenant_id = own)` matching has served traffic. Only roll the data back if you are also rolling back the application code to a build that still understands the NULL-shared slot; otherwise leave rows adopted and roll back code only. The adoption step is idempotent (guards on `tenant_id IS NULL`, no-ops when the root tenant does not exist) and safe to re-run. See [rollback.md](rollback.md) Change-Specific Rollback: Strict Tenant Isolation.
